## 1. GAS にコードを貼る

ファイルは **2 枚**です。Apps Script は全ファイルでグローバルスコープを共有するので、
分かれていても動きは変わりません。**並び順は関係ありません。**

| GAS 側のファイル名 | 貼る中身 | 貼り替え頻度 |
|---|---|---|
| `コード` | `fortinet_psirt_watcher_v7.gs` | 変更のたび |
| `tests` | `fortinet_psirt_watcher_v7_tests.gs` | ほとんど無い |

**初回だけ 2 枚**

1. スプレッドシートを開く → **拡張機能 → Apps Script**
2. 既存コードを `fortinet_psirt_watcher_v7.gs` の全文で置き換え
3. 左の **ファイル → ＋ → スクリプト** で `tests` を作り、
   `fortinet_psirt_watcher_v7_tests.gs` の全文を貼る（初期の `function myFunction() {}` は消す）
4. **保存**（Ctrl+S）

**2 回目以降は `コード` だけ**貼り替えれば済みます。

> **注意**: 確認用の中身を `コード` の側に貼り足さないこと。同じ関数が 2 回定義され、
> あとに読まれた方が勝ちます。エラーは出ないので気づけません。

## 2. スクリプト プロパティ（未設定なら）

**プロジェクトの設定 → スクリプト プロパティ**

| キー | 用途 |
|---|---|
| `GEMINI_API_KEY` | 影響機能・確認方法・ユーザ影響（Fortinet 判定用の機能分類も含む） |
| `ANTHROPIC_API_KEY` | `AI_PROVIDER = 'claude'` に切り替えたときだけ使う（モデルは Haiku） |
| `SLACK_WEBHOOK_URL` | Slack 通知の宛先「個人検証」（任意） |
| `SLACK_WEBHOOK_URL_TEAM` | Slack 通知の宛先「会社テスト」（任意） |
| `SLACK_TARGET` | 日次 `main()` の宛先。`personal` / `team`。**未設定なら `personal`** |
| `JPCERT_SEEN_AT` | 通知済みの JPCERT 注意喚起 ID。**ツールが自動で書きます。触らないこと**（消すと過去の注意喚起がもう一度流れます） |

`SLACK_TARGET` は普段は未設定のままにします。会社テストチャンネルへ実データを流したいときだけ
`team` を入れ、確認が済んだらキーごと削除してください。値を打ち間違えても通知は止まらず、
警告をログに残して `personal` へ送ります（設定ミスが「静かな日」と区別できなくなるのを避けるため）。
`team` のまま実行した日は、実行履歴の「備考」に `Slack宛先: 会社テスト` が残ります。

AI は既定で Gemini。Gemini が HTTP 503（モデル側の一時的な過負荷）を返す日があり、
その場合は `AI_PROVIDER` を `'claude'` にすると回避できます。日次上限（429・本文に `PerDay`）
とは別物で、503 ではフォールバックモデルへの退避は起きません。

**Cisco openVuln API は GAS では使わない。**  
Key/Secret 自体は有効（手元 `curl` で確認済み）だが、`UrlFetchApp` が `id.cisco.com` で Access Denied になる。  
`CISCO_API_CLIENT_*` は不要です。Cisco の更新先版番号は次のいずれかになります。

- CSAF の Workarounds から取れたコマンド（あれば）
- 「更新先はアドバイザリで確認」（セルがアドバイザリへのリンク）

**メール通知は2種類**（どちらも実行アカウント宛。初回にメール送信権限の承認が必要）

| 件名 | 出るとき |
|---|---|
| `[脆弱性ウォッチャー] main() 失敗` | `main()` が例外で止まった |
| `[脆弱性ウォッチャー] CSAF 取得失敗 N 件（ベンダー）` | 一度も処理できていないアドバイザリの CSAF が取れなかった |

記録済みの件が一時的に取れなかっただけならメールは飛びません（翌日の取得で解決するため）。

## 3. 移行（列構成が変わった場合）

```
① migrateLedgerHeaders()   ← 台帳13列 / 処理済み10列に見出しを更新
② migrateAssetHeaders()    ← 資産9列（更新日を含む）に見出しを更新
③ reprocessFortinet()      ← Fortinet の処理済み・台帳を作り直す（Slack 1通）
④ reprocessCisco()         ← Cisco の処理済み・台帳を作り直す（Slack 1通）
```

**実行履歴シートは移行操作が要りません。**見出しが古ければ次の `main()` で自動更新され、
列数が減った場合は右端の古い見出しも削除されます。ただし**列の意味が変わった回は、
データ行を手で削除**してください（古い行が新しい見出しの下に残ると誤読します）。

`migrateAssetHeaders()` は**入力済みの資産を消しません**。すでに v7 構成なら見出しだけ
差し替えます（以前は全消しして初期値に戻す作りでした）。

`clearRunData()`（メニュー「脆弱性ウォッチャー → データ削除」）は台帳と処理済みを
両方空にします。資産シートは触りません。ベンダー単位で作り直すだけなら ③④ で足ります。

**③④ が必要な理由**: 処理済みシートは追記型で、既存行を書き換えません。
列を増やしたり意味を変えたりしても、既存行は空欄や旧構成のまま残ります。

## 5. 本番取得

```
main()
```

### 取得の動き（ベンダーで違います）

| | Fortinet | Cisco |
|---|---|---|
| 一覧 | `ir.xml`（最新50件・改訂順） | `csaf_20.xml`（最新50件） |
| CSAF の取得 | **毎回50件すべて** | 前回から更新のあった分だけ |
| 既読の判定 | CSAF の `current_release_date` と版 | 同左 |

Fortinet が全件取得なのは、**RSS の日付が CSAF の改訂を表さない**ためです。
実測で、RSS の `Revised on` だけが動いて CSAF が変わらない件が6件、
逆に RSS が動かないまま CSAF だけ改訂される件が2件あり、49件中41件でしか一致しませんでした。
RSS の日付で候補を絞ると、後者を永久に見逃します。
Cisco の `csaf_20.xml` は CSAF から生成されており50/50で一致するため、差分取得で問題ありません。

所要時間は差分ゼロの日で 10秒前後（Fortinet の50件並列取得が約3〜5秒）。

**CSAF が取得できなかった場合**も、RSS にある CVSS と説明文で台帳に行を作ります
（`あり（影響調査）`・判定根拠は「CSAF を取得できず版比較できないため」）。
アドバイザリページからの取得は**できません**。ボット対策により
`Just a moment — verifying connection security` の待機ページしか返らないためです。

### 期待される結果

**台帳（13列・左6列固定）** — 対応要否を判断する作業リスト

`最終更新日 | 自社影響 | 製品 | CVE | CVSS | KEV | 脆弱性名 | ユーザ影響 | 影響機能 | 判定根拠 | 確認方法 | 公式推奨対応 | アドバイザリ`

列は確認者の読み順に並んでいます。
「いつ検知した何か → どれくらい危ないか → どんな影響か → なぜその判定か → 何を確認しどう直すか → 公式で裏を取る」。
左6列（最終更新日〜KEV）を固定表示するので、右へスクロールしても判断材料が残ります。
並び順は `自社影響` 順（第2キーが最終更新日の降順）。作業リストなので、
未処理の重い行が新しい「なし」の下に沈まないようにしています。

自社影響は Fortinet / Cisco 共通で **あり（対応検討）/ あり（影響調査）/ なし** の3値。
判定根拠と基準は [社内ルール案_OS更新基準.md](社内ルール案_OS更新基準.md) を参照。

| 判定 | 出やすい理由 | 次の行動 |
|---|---|---|
| あり（対応検討） | 常時有効な機能に、外部から無認証で掌握・業務停止に至る欠陥 | 対応時期を検討する |
| あり（影響調査） | 影響機能が設定次第（管理GUI / VPN / UTM など）／版が不明 | 確認方法を実機で実行して振り分ける |
| なし | `PR:H` `PR:L` `AV:L` `AV:P` `AV:A` `UI:R` のいずれか／SSL-VPN 無効／軽微 | 記録のみ |

**脆弱性名**: CSAF / RSS の文書タイトル（最大60字）。パッと見で何の脆弱性か分かるようにする  
**判定根拠**: 2行。1行目 `OS=対象 | KEV=なし`、2行目 `◯◯のため「あり（影響調査）」`  
**確認方法**: 3行（何を見る／何を打つ／どう判断する）。ラベルは表示時に除去  
**ユーザ影響**: 最悪ケース50字以内  
**公式推奨対応**: 英語を出さない。Cisco は回避策コマンドがあればそれ、無ければ「回避策なし。更新先はアドバイザリで確認」（テキスト。リンクはアドバイザリ列）  
**確認方法**: 版該否は済み。設定次第なら設定確認、常時有効なら次アクション（定期更新枠など）  
**ユーザ影響**: CVSS の C/I/A に合わせる（DoS なのに掌握、は出さない）  
**Slack（日次1通）**: 新着がなければ送らない。あるときだけ1通。
末尾に **JPCERT/CC 注意喚起** の枠が付くことがあります。自社ベンダー（資産シートの
ベンダー・製品）の名前が題名に入った注意喚起が新しく出たときだけで、年に数件です。
**判定はしていません**（CVE を持たない回があるため突き合わせ不可）。リンクを開いて
人が判断してください。CVE の該当が 0 件の日でも、注意喚起があれば1通届きます。
1通に個別表示するのは最大15件。超えたときだけ末尾に `全 N 件のうち M 件を表示` が出ます。  
1行目が本体: `新しい脆弱性が発表されました🔍`。2行目: `FortiGate:1件 Cisco:2件`。フッターは `Security NEXTで確認  /  判定台帳を確認`（URLは出さない）。  
各件: `CVE  /  CVSS 5 [中]  /  08/12更新` → 機器 → 内容（AIの日本語要約。無ければタイトルの日本語訳） → 影響 → 推奨対応。  
**台帳に載らない行**: 非保有製品と版が影響範囲外の行（処理済みシートには残る）

**処理済み（10列）** — ベンダーが公表した全件の記録。分母であり、除外の根拠

`最終更新日 | 初回公表日 | ベンダー | CVE | タイトル | 自社判定 | 判定根拠 | 対象製品 | アドバイザリID | CSAF版`

「今月10件公表されたが対象は5件。残り5件はなぜ対象外だったのか」を確認するためのシートです。
日付を2つ並べているのは、同じ日なら初出・違えば改訂と判別するためです。

| 自社判定 | 意味 | 判定根拠の例 |
|---|---|---|
| `対象` | 保有製品があり、自社の版が影響範囲内 | `FortiOS 7.4.11｜影響範囲内` |
| `対象外-OS影響外` | 保有しているが版が影響範囲外 | `FortiOS 7.4.11｜7.4 系の影響は 7.4.8 まで` |
| `対象外-未保有` | 該当する自社製品を持っていない | `資産に該当する製品が無い` |
| `対象外-情報通知` | 脆弱性ではなく公開一覧のお知らせ（Cisco の Advance Notification） | `脆弱性ではなく公開一覧のお知らせ` |
| `判定不能` | CSAF を取得できず判断できなかった | `CSAF を取得できず判定できない` |

値の先頭が `対象` / `対象外` / `判定不能` で揃っているので、列を眺めるだけで可否が読めます。
`アドバイザリID` はリンクになっており、公式ページを開けます（セルの値は ID のままなので
既読判定には影響しません）。`CSAF版` は Fortinet では常に `0` で、
CSAF を読めなかった行だけ `未取得` と入ります。

`countByMonth()` / `countByMonthVendor()` は**情報通知を除いて**数え、
除外件数をログに併記します。

---

**月次サマリ草案（Google ドキュメント）**

メニュー **脆弱性ウォッチャー → 月次サマリ草案を作る（先月分）**。
月を指定するなら `buildMonthlyReport('2026-08')`。新しい Google ドキュメントができ、
URL がログとシート右下のトーストに出ます。

処理済み・台帳・判断記録・実行履歴の4シートを突き合わせて、次の5節を並べます。

1. 今月の全体像（公表件数・自社対象・判定内訳）
2. 対応の検討・調査が要る行
3. 人が下した判断（判断記録から）
4. 対応不要と判定した行とその根拠
5. ツールの稼働状況（**実行されなかった日があればそう書きます**）

**文章は書きません。**数字と行を並べるところまでで、結論は人が書いてください。
だから「草案」です。

---

**判断記録（7列）** — 人が下した対応の判断。ツールは書きません

`判断日 | アドバイザリID | CVE | 判断 | 根拠 | 判断者 | 対象時点`

**使い方**: 台帳で行を選び、メニュー **脆弱性ウォッチャー → 選択行から判断記録を作る**。
判断記録シートに行ができるので、`判断`（プルダウン）と `根拠` を埋めます。

| 判断 | 台帳の自社影響 | Slack |
|---|---|---|
| 対応不要（定期更新枠） | `なし` に変わる | 出なくなる |
| 対応済み | `なし` に変わる | 出なくなる |
| 対応する（実施待ち） | `あり（対応検討）` | 出る |
| 保留 | 変わらない | 変わらない |

判定根拠には `2026-09-01 に saitoh が「対応不要（定期更新枠）」と判断（…）` と入ります。

**アドバイザリが改訂されると判断は無効になり、また出てきます。**
判断は「その時点の内容」に対して下したものなので、影響範囲や修正版が変わったら
もう一度見る必要があります。`対象時点` 列がその判定に使われます。手で書かず、
必ずメニューから行を起こしてください（空欄だとその行は無視されます）。

`CVE` を空にすると、そのアドバイザリの全 CVE に効きます。

---

**実行履歴（11列）** — 1実行1行。動いた事実そのものの記録

`実行日時 | 結果 | 確認件数 | 差分なし | 更新あり | 対象 | 対象以外 | 失敗 | 所要秒 | AI呼び出し | 備考`

Slack は該当ありの日だけ鳴るため、「該当なしだった日」「取得に失敗した日」
「トリガーが消えて実行されなかった日」がすべて同じ静けさに見えます。
実行ログの保持期間も短く後から遡れないので、動いた事実だけをここに残します。
**行が途切れていれば実行されていない日**です。

数字は左から右へ一直線に読めます。`確認件数 = 差分なし + 更新あり`、
`更新あり = 対象 + 対象以外`。単位はアドバイザリ件数で、台帳の行数ではありません
（1 アドバイザリが CVE × 製品で複数行に開くため一致しません）。

`対象以外` には、未保有・OS影響外・情報通知に加えて **判定不能**（CSAF が取れなかった件）
も入ります。だから「対象外」ではなく「対象以外」です。内訳は `備考` の `判定[…]` に出ます。

`備考` は更新・失敗・エラーがあった日だけ書き、平常日は空欄です。
**何か書いてある行が見るべき行**になります。

`結果` は `正常` / `要確認`（取得失敗あり）/ `失敗`（実行が途中で止まった）。
落ちた実行も記録されます。

---

**資産（9列）**

`ベンダー | 種別 | 製品 | 機種 | バージョン | 台数 | ツール対象 | 備考 | 更新日`

`更新日` は棚卸しした日を人が手で入れる欄で、ツールは書き込みません。
判定はバージョンの突き合わせで行うため、この表がいつ時点のものか分からないと
判定の根拠も定まりません。

### Slack 通知の目的

1. **気づく** — 自社該当の脆弱性公開に気づく  
2. **簡潔にわかる** — CVE・版・機能・被害を2秒で掴む  
3. **公式で決める** — アドバイザリIDリンクから一次情報で対応を決める  
4. **必要なら詳細** — 台帳リンクは任意

通知は最終決定の場ではない。決定は公式アドバイザリ側で行う。

**表示確認のしかたは 3 通りあります。**

| やりたいこと | 方法 | 送信 |
|---|---|---|
| JSON を目で見る | `testSlackBlocks()` | しない |
| チャンネルでの見え方を見る | メニュー **脆弱性ウォッチャー → Slack テスト送信 → 個人検証／会社テスト** | サンプル3件を送る |
| 実データの見え方を見せる | `SLACK_TARGET=team` にして `reprocessCisco()` | 本番と同じ経路で1通 |

メニューのテスト送信は架空の CVE（`CVE-2026-0001` など）です。本物の公表と読み違えられないよう、
先頭に「表示確認のテスト送信です」の1行が付きます。送信結果はシート右下のトーストにも出ます。

## 6. うまくいかないとき

| 症状 | 対処 |
|---|---|
| 台帳・処理済みの列がずれる | `migrateLedgerHeaders()` → `reprocessFortinet()` → `reprocessCisco()` |
| 処理済みの自社判定・判定根拠が空欄 | 追記型なので既存行は書き換わらない。`reprocessFortinet()` / `reprocessCisco()` で作り直す |
| 実行履歴の見出しが古い | 次の `main()` で自動更新される。列の意味が変わった回はデータ行を手で削除する |
| 資産シートの列を増やしたい | `migrateAssetHeaders()`。入力済みの資産は消えない |
| 旧語彙（対応推奨など）が残る | `clearRunData()` を実行していない。実行して `main()` |
| 影響機能が空 | `GEMINI_API_KEY` 確認。未設定時は機能推定＋確認手順テーブルのフォールバック |
| `AI 生成: gemini / 成功 0` | `gemini-3.7-flash` 無料枠（1日20回程度）切れ。現行コードは `gemini-3.6-flash` → `2.5` → `2.0` へ退避。リセットは太平洋時間の0時 |
| `HTTP 503 (gemini-…) のため … 再試行します` | 無料枠切れではなくモデル側の一時的な過負荷。3回リトライして諦め、表示列はコードのフォールバックで埋まる。頻発するなら `AI_PROVIDER = 'claude'` |
| 確認方法が「アドバイザリを確認」だけ | コード側で機能別手順に差し替える想定。再実行後も残るなら報告 |
| 「あり（影響調査）」ばかり | 影響機能が `config` なら正しい挙動。確認方法を実行して振り分ける |
| Cisco の公式推奨対応が「参照」だけ | 想定どおり（GAS では openVuln 不可）。回避策コマンドが CSAF にあればそちらが出る |
| `cisco-sa-notice-*` が台帳に出る | 事前告知であり脆弱性ではない。現行コードでは台帳に出さない。出たらコード貼り替え漏れ |
| `CSAF未作成 1` が毎日ログに出る | 正常。FG-IR-22-059 は Fortinet が CSAF を出す前（2025年3月以前）の案件で、CSAF が存在しない。RSS には改訂のたびに載り続ける |
| `AI 呼び出し` が想定より多い | リトライとモデルのフォールバックも1回ずつ数えている。プロンプト数の数倍なら 429/503 が多発している |
| 実行履歴に行が無い日がある | その日は実行されていない（トリガーが消えた等）。`main()` は落ちても `finally` で行を残すので、行が無い＝未実行 |
| Cisco が台帳に出ない | `main()` が空台帳なら一度再取得する。まだなら `reprocessCisco()`。台帳だけ消しても処理済みが残ると再取得しない |
| データ削除で「固定されていない行をすべて削除することはできません」 | 見出し固定のまま全行 delete していた。現行コードは中身を消す。貼り替えてメニューから再実行 |
| KEV 照合失敗 | ログの `KEV 照合失敗` → ネットワーク確認 |
