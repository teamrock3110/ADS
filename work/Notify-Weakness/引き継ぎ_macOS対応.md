## 0. 最初に決めること（実装より先）

**「macOS を同じ台帳に載せるべきか」を最初に決める。** ここを飛ばして実装すると、
あとから台帳の意味が壊れる。

いまのツールは全体が **「CVE × 製品 → 自社が持っている版と数値比較 → 社内ルールで判定」**
という形に寄っている。台帳の1行は「1つの CVE が、1つの製品に影響する」という単位。

macOS の要件がどちらかで、設計が変わる。

| 要件 | 相乗りできるか |
|---|---|
| **A. macOS の脆弱性を知りたい**（14.7.1 に CVE-xxxx が出た） | **できる。**取得元を1本足すだけ。判定・台帳・Slack は既存のまま |
| **B. macOS の新しい版が出たことを知りたい**（14.7.2 がリリースされた） | **形が違う。**起点が「脆弱性」ではなく「リリース」。台帳の「自社影響」「判定根拠」が意味を成さない |

**利用者の言葉は「リリースと更新内容を検知する」だったので、B の可能性が高い。**
その場合、同じ台帳に載せると次の問題が出る。

- 台帳の `自社影響`（あり(対応検討)/あり(影響調査)/なし）は**社内ルールの条件1〜4**で決まる。
  リリース情報に条件3（AV:N/PR:N/UI:N）も条件4（C/I/A）も無い
- `判定根拠` は `OS=対象 | KEV=なし` ＋理由の2行。リリースには KEV も OS 該当も無い
- `CVSS` `CVE` `影響機能` `確認方法` が全部空になる。**README §4.1「空欄に意味を持たせない」に反する**

**要件を聞いたら、まず A か B かを利用者に確認すること。** B なら別シート・別通知枠を勧める。
「同じ台帳に載せたい」と言われたら、上の4点を示してから決めてもらう。

## 1. このツールの現状（2026-09-08）

`fortinet_psirt_watcher_v7.gs` 4,614行・178関数。Google スプレッドシート + Apps Script。
毎朝9時台に Fortinet / Cisco の脆弱性を取得し、自社資産に当たる CVE だけ台帳へ書き、

削減の大半は「使っていない機能」で、利用者に一覧を見せて「使ってる？」と聞いて出た。

### main() の骨格

```javascript
function main() {
  startRunStats_();
  try {
    const fortinetRows = runFortinet_();   // ← ここに macOS を足すことになる
    const ciscoRows = runCisco_();
    const notifyRows = fortinetRows.concat(ciscoRows);
    const alerts = newJpcertAlerts_(readAssets_());   // 判定に混ぜない別枠
    if (notifyRows.length || alerts.length) {
      if (notifySlack_(notifyRows, alerts)) markJpcertSeen_(alerts);
    }
  } catch (e) { ... } finally { writeRunLog_(runError); }
}
```

ベンダーごとに `runXxx_()` があり、それぞれが台帳の行の配列を返す。
**A の要件なら `runMacOS_()` を足して concat するだけで済む。**

### シートは5枚

| シート | 中身 |
|---|---|
| 台帳（14列） | 判断が要る行だけ。作業リスト |
| 処理済み（10列） | 公表全件の記録。分母であり、除外の根拠 |
| 実行履歴（11列） | 1実行1行。動いた事実。**行が無い＝未実行** |
| 資産（9列） | `ベンダー / 種別 / 製品 / 機種 / バージョン / 台数 / ツール対象 / 備考 / 更新日` |
| 判断記録（7列） | 人の判断。ツールは書かない |

## 2. すぐ使える事実

### 資産シートに Apple / macOS を足すと、JPCERT は自動で拾う

`jpcertKeywords_` が**資産シートの `ベンダー` と `製品` 列から当てる語を自動生成**している
（`ツール対象=いいえ` の行は除外）。行を足すだけでコード変更は要らない。

ただしこれは **JPCERT/CC の注意喚起（`/at/`）だけ**で、年29件のうち自社該当は数件。
**通常のリリース公開は拾えない。**「緊急に対応すべき事象」しか出ないため。

### ベンダー定数の足し方

```javascript
var VENDOR_FORTINET = 'Fortinet';
var VENDOR_CISCO    = 'Cisco';
```

**`var` で宣言すること。`const` にすると確認用ファイルから見えない**（下記 §4）。

### 既読管理の仕組み

処理済みシートの `アドバイザリID` と `CSAF版` / `最終更新日` で「もう処理したか」を判断する
（`needsAdvisoryProcessing_`）。macOS でも同じ仕組みに乗せられるなら、
「同じリリースを毎日通知する」問題は自動で解決する。

**乗せられない場合は必ず別の既読管理を作ること。**無いと毎日同じものが Slack に出る。

## 4. 実装で必ず踏む罠

### Apps Script は別ファイルのトップレベル `const` が見えない

確認用ファイル（`test.gs`）から参照する定数は、本体側で **`var`** にする。
実測で `V_INVEST` が `ReferenceError` になった。`testSharedConstants()` が番人で、
**他のテストより先に実行する**。新しい定数を確認用から参照したくなったら、
`var` に変えて `testSharedConstants()` の一覧にも足す。

**node で2ファイルを連結して検証してもこの問題は再現しない**（1スコープになる）。
分離が絡む変更は実機で確かめること。

### デプロイは手貼り

GAS エディタへ `main.gs` / `test.gs` / `readme.gs` の3枚を貼る。clasp は見送り済み。
**実装した内容が GAS に入っているとは限らない**ので、区切りで「貼ったか」を確認する。

### AI は同じ入力でも日によって違う答えを返す

抜き取り検証で「たまたま良かった日」を見ても意味がない。
コード側の保険で決定的にして、テストで押さえること。

### GAS の制約（実測）

実行6分制限（50件の全再処理で到達実績あり）。差分ゼロの実行は7〜10秒。
Gemini 無料枠は1日20回程度でモデル別に別枠。UrlFetch は 20,000回/日。

## 5. 進め方（利用者の希望）

- **次の作業は必ず聞いてから動く。**勝手に機能追加しない
- コミット・push は依頼があるまでしない
- 結論ファーストで答える。手順の羅列や過度な言い換えは不要
- **「なぜその値・その設計か」を必ず問われる。**根拠のない断定をすると指摘される。
  適当に置いた値は「根拠はない」と正直に言うこと
- **「パッチワークになっていないか」「ベストプラクティスと言えるか」を繰り返し問われる。**
  当てはまらない場合は正直にそう答え、何が構造的で何が対症療法かを分けて示す
- **知らないことは調べる。**推測で答えない（モデルIDは `ai.google.dev` で確認する、など）
- 実装前に設計を詰めたがる。選択肢を出し、推奨と理由を添えること

### 見積もりを出すときの注意（2026-09-08 に実際に失敗した）

行数や工数の見積もりを出すとき、**行数だけを見て依存関係を確認せずに数字を言わないこと。**
「449行削れる」と言って実績147行だった。原因は、テストからの参照・外部からの呼び出し・
副作用を確認する前に数字を出したこと。**必ず先に確認してから言う。**
