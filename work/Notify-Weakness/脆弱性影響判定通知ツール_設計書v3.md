# 設計書v3：脆弱性 影響判定・通知ツール

**文書の位置づけ**
v2 を置き換える。v2 からの変更点は 2 つの入力による。

1. **実データによる検証**（2026-08-11 実施）。v2 で【未検証】としていた前提を、Fortinet PSIRT の RSS 50 件・CSAF 97 要素を実際に取得して確かめた。前提が 3 つ覆り、うち 1 つは v2 の判定基準の骨格に影響する。
2. **設計レビュー**（ChatGPT による台帳レビュー）。出力の可読性について指摘を受けた。ほぼ全面的に採用した。採用しなかった 1 点は理由を明記する。

**記載ルール**
- 【確定】合意済み。変更する場合は理由を明示すること
- 【変更】v2 から変えた箇所。理由を併記している
- 【検証済】実データで確認した。日付と件数を併記する
- 【未検証】前提として置いているが、一次情報・実データで確認していない
- 【未決】まだ決めていない

## 1. 検証結果（v2 の【未検証】に対する回答）

2026-08-11 に、Fortinet PSIRT の RSS 50 件と、そこから辿れる CSAF 97 要素をすべて取得して確認した。

> **CSAF とは**：Fortinet が脆弱性情報を機械可読な JSON で公開しているファイル。HTML を読み取らなくても、影響バージョン・修正版・CVSS・影響の種類が構造化された状態で入っている。

### 1.1 緩和策（Workarounds）は、ほぼ公開されていない【検証済・重要】

**97 要素すべてで `Workarounds` は `N/A` だった。実質的な緩和策の記載は 0 件。**

これは v2 の骨格に対する反証である。v2 は次の 2 点を緩和策の上に組み立てていた。

- §3.2：PSIRT を一次ソースに選んだ理由の一つが「更新せずに危険を下げる方法は PSIRT にしかない」
- §6.2：対応期限を「更新」ではなく「対応（更新または緩和）」に対して切る。**これが期限表が成立する条件だった**

緩和策が自動で取れない以上、「3日以内に緩和策を適用する」という期限は、**自動では何も埋まらない欄**になる。期限だけが残り、中身は毎回人が探すことになる。それは v2 §1.3 で問題視した「証明責任が担当者個人に来る」構造そのものである。

**対応**：
- 緩和策の取得処理自体は残す（記載があれば拾う。将来 Critical 系で出る可能性はある）
- ただし**独立列は作らない**。記載があるときだけ `対応` に含める（レビュー指摘10と同じ結論）
- **§6.2 の期限表は保留**とする。緩和策を前提にした期限設計は、緩和策の供給源を確保してから決める（後述 6.3）

*この検証範囲の限界*：RSS が保持する直近 50 件（FG-IR-24-257 〜 FG-IR-26-154）を見た結果である。過去の Critical 系アドバイザリ（SSL-VPN の無効化を促したものなど）には緩和策の記載があった可能性がある。「Fortinet は緩和策を書かない」ではなく「**直近 50 件では 0 件だった**」が正確な言い方である。

### 1.2 CSAF の `vulnerabilities[]` が、そのまま「CVE × 製品」の粒度だった【検証済】

50 アドバイザリ → **97 要素**。そして、

- **1 要素に複数の製品系列が混在した例は 0 件**
- 行キー `(FG-IR, CVE, 製品)` の重複は **0 / 97**
- 各要素が固有の `product_status.known_affected` / `scores` / `remediations` を持つ

つまり **レビューが要求した行の単位は、Fortinet が公開しているデータ構造そのもの**だった。分割ロジックを自作する必要はなく、v5 が `pushUnique_` で全要素を 1 行に**まとめていた処理をやめるだけ**でよい。

実例（FG-IR-26-154）：

| 要素 | CVE | 製品 | 影響バージョン | 修正 |
|---|---|---|---|---|
| 1 | CVE-2025-43892 | FortiOS | >=7.4.0\|<=7.4.8 ほか | 7.4.9 以上 |
| 2 | CVE-2026-59840 | FortiOS | >=7.4.0\|<=7.4.8 ほか | 7.4.9 以上 |
| 3 | CVE-2026-59840 | FortiProxy | >=7.4.0\|<=7.4.13 ほか | 7.4.14 以上 |

v5 はこれを 1 行に潰し、CVE 欄に `CVE-2025-43892, CVE-2026-59840`、影響バージョン欄に FortiOS と FortiProxy を混在させていた。レビュー指摘2が問題にした「どの CVSS がどの CVE のものか分からない」は、この潰し込みが原因である。

### 1.3 CSAF の URL は RSS から導出できる【検証済】

v5 はアドバイザリ HTML を取得し、`csaf_url=(https://...json)` を正規表現で拾っていた。実装設計書はこれを「HTML 依存はこの 1 箇所のみ」と書いていたが、依存自体を無くせる。

```
https://filestore.fortinet.com/fortiguard/psirt/csaf_<タイトルのスラッグ>_<fg-ir-番号(小文字)>.json
```

スラッグは「小文字化 → 英数字以外をハイフンに → 連続ハイフンを1つに」。**RSS 50 件すべてでこの規則から正しい URL を組み立てられた（50/50）。**

得られるもの：
- 取得先が `filestore.fortinet.com` だけになる（`fortiguard.fortinet.com` は社内プロキシで遮断される環境がある。実際に本検証環境では遮断されていた）
- 通信回数がアドバイザリあたり 2 回から 1 回に減る
- HTML の構造変更に影響されなくなる

保険として HTML 経由の経路はコードに残す（スラッグ導出が 200 を返さなかった場合のみ実行）。

### 1.4 NVD API は不要【検証済・v2 §3.2 から変更】

v2 は CVE 本体・CPE・影響バージョン範囲・CVSS を NVD から取る設計だった。CSAF に全部入っている。

| v2 が NVD に求めていたもの | CSAF での所在 |
|---|---|
| CVE 本体 | `vulnerabilities[].cve` |
| 影響バージョン範囲 | `vulnerabilities[].product_status.known_affected` |
| CVSS | `vulnerabilities[].scores[].cvss_v3` |
| 対象製品 | `vulnerabilities[].scores[].products` |
| 修正版 | `vulnerabilities[].remediations[]`（`category: vendor_fix`） |
| 公開日 | `document.tracking.initial_release_date` |

**NVD を外すことで、v2 §11.4「NVD の CPE 付与遅延」は未決事項から消える。** CPE パターンも不要になるため、製品台帳から `cpe_pattern` 列を削除する。

### 1.5 影響バージョンの表記は 7 種類【検証済】

バージョン比較をコードで書くために、`known_affected` の表記を全件分類した（延べ 340 件）。

| 表記 | 件数 | 例 |
|---|---|---|
| `>=A\|<=B`（範囲） | 137 | `FortiOS >=7.4.0\|<=7.4.7` |
| `X.Y all versions`（系列全体） | 127 | `FortiOS 7.2 all versions` |
| `X.Y.Z`（単一） | 13 | `FortiOS 7.6.0` |
| `X.Y.Z and above`（下限のみ） | 3 | `FortiNDR 7.2.2 and above` |
| `all versions`（製品全体） | 2 | `FortiSandbox Cloud all versions` |
| `>=X.Y\|<=A.B.C`（2桁の下限） | 1 | `FortiProxy >=7.4\|<=7.4.13` |
| 非数値を含む | 1 | `FortiSASE 25.1.c` |

最後の 1 件は数値比較できない。**推測せず `要確認` に落とす。**

注意点として、製品名に空白を含むものがある（`FortiSOAR PaaS` / `FortiAnalyzer Cloud` / `FortiSOAR on-premise`）。文字列の先頭 1 語を製品名とみなす実装は誤る。製品名は `scores[].products` から取る。

### 1.6 `vulnerabilities[].title` は脆弱性名ではない【検証済】

`FortiOS - LOW - FG-IR-24-257` のような、製品・深刻度・ID を並べた内部管理用の文字列だった（38/38 件で `document.title` と不一致）。

脆弱性名は `document.title`（例：`Information Disclosure on SSLVPN endpoint`）を使う。

### 1.7 その他の実測値【検証済】

| 項目 | 実測 |
|---|---|
| CVSS のバージョン | 97 件すべて v3。v4 は 0 件（コードは v4 も読めるようにしておく） |
| CVE 未採番の要素 | 0 件 |
| 深刻度の分布 | MEDIUM 68 / LOW 15 / CRITICAL 8 / HIGH 6 |
| 修正指示の文型 | `Upgrade to N or above` 159 / `Migrate to a fixed release` 175 / `Not Applicable` 107 |
| 複数アドバイザリに跨る CVE | 0 件 |

`Migrate to a fixed release` は「その系列に修正版はない。上位系列へ移行せよ」の意味であり、パッチ適用とは作業量が桁違いになる。**この区別は出力に出す。**

### 1.8 脆弱性情報を持たないアドバイザリが存在する【検証済・分母に直結】

**50 件中 3 件は、CSAF に `vulnerabilities` キー自体が無い。** `product_tree` も空で、使える情報はタイトル・公開日・URL だけである。

| FG-IR | タイトル | 公開日 |
|---|---|---|
| FG-IR-26-126 | Axios npm Package Compromised | 2026-04-14 |
| FG-IR-26-139 | Linux Kernel Vulnerability copy.fail - CVE-2026-31431 | 2026-05-13 |
| FG-IR-26-144 | Linux Kernel vulnerability Dirty Frag | 2026-06-03 |

いずれも**他社製コンポーネント由来**（Linux Kernel、npm パッケージ）の告知である。Fortinet 製品への影響範囲が機械可読な形では公開されていない。

**これは分母を壊す。** 初回運用で実際に発生した。`vulnerabilities[]` を素直に展開すると行が 1 つも作られず、行が無いということはアドバイザリ列に FG-IR が残らないため既読にもならない。結果として二重の実害が出る。

1. **分母から永久に欠落する。** 「今月 Fortinet から公表：N 件」が過少になる。本ツールの第一目的が壊れる
2. **毎回取得し直す。** 既読にならないため、`MAX_ADVISORIES_PER_RUN` の枠を恒久的に消費し続ける

初回実行では RSS 先頭 25 件を処理して台帳に 23 件しか残らず、この 2 件（FG-IR-26-139 / FG-IR-26-144）が消えていた。

**対応**：`vulnerabilities` が空なら `要確認` の行を 1 件立てる（`noVulnRow_`）。タイトルに CVE 番号が含まれていれば拾う。判定はせず、アドバイザリ本文を人が読む前提で Slack に流す。

*設計上の教訓*：**「該当行が 0 件」と「取得できなかった」は区別しなければならない。** 前者を黙って捨てると、捨てた事実ごと消える。分母を主張するツールでは、処理したすべてのアドバイザリが必ず 1 行以上を残す必要がある。

### 1.9 資産シートの登録漏れは、静かな見逃しになる【構造的リスク】

自社影響は資産シートの記載だけを根拠にしている。登録が無ければ `なし`「自社では保有していない」と断定する。**登録漏れがあっても、ツールにはエラーが出ない。**

しかも根拠欄は「資産シートに未登録のため」と正直に書くが、**それを読むのは対象外の行を開いたときだけであり、対象外は普通読まれない。** `あり` の見逃しゼロが必須（6.4）である以上、これは最も危険な失敗の型である。

**対応**：資産シートに無いことを理由に `なし` にした製品を、実行のたびにログへ一覧する（`logUnownedProducts_`）。前提を毎回目に見える場所に出す。

根本的な解決は資産シートを正しく保つ運用であり、これは 6.3-7（`version_checked_at` と確認タイミングの運用ルール化）と同じ問題である。10 月の新運用策定に含める。

*なお初回運用時、v3 初版の 3.1 が FortiClient / FortiClient EMS をスコープに含めていたため、これらが資産未登録であることを登録漏れと判断したが、**誤りだった**。利用者への確認により、この 2 製品は判定対象外であることが確定した（3.1）。実際の登録漏れではなく、設計書側のスコープ記載が実態と合っていなかった。*

### 1.10 アドバイザリは改訂される。FG-IR だけの既読判定では見落とす【検証済・見逃し経路】

RSS には「新しく公表されたもの」だけでなく「**既存のものが改訂されて再浮上したもの**」が入る。実測で 50 件中 **6 件が改訂もの**だった。

| FG-IR | 初回公表 | 最終更新 | FortiOS を含むか |
|---|---|---|---|
| FG-IR-25-122 | 2025-03-11 | **2026-04-14** | |
| FG-IR-24-257 | 2025-06-10 | **2025-08-08** | ★ |
| FG-IR-24-452 | 2025-10-14 | **2026-01-14** | ★ |
| FG-IR-25-545 | 2025-11-18 | **2026-01-14** | ★ |
| FG-IR-26-128 | 2026-05-12 | **2026-05-13** | |
| FG-IR-26-139 | 2026-05-13 | **2026-06-08** | |

改訂の中身は、分析が進むにつれた**影響製品・影響バージョンの追加**である。FG-IR-25-122（OpenSSH）は初回公表から 1 年後の改訂で対象製品が 6 製品に増えていた。

**ここに見逃し経路がある。**

- 改訂されても **FG-IR 番号は変わらない**
- RSS の `pubDate` も **初回公表日のまま動かない**（実測 50/50 で `initial_release_date` と一致）
- したがって「最終更新日」は **CSAF を開かないと分からない**

FG-IR だけで既読判定していると、次が起きる。

```
1回目  FG-IR-25-545 を取得 → 影響は FortiOS 7.6 系のみ → 対象外 → 記録
        ↓
改訂    Fortinet が FortiOS 7.4 系を影響範囲に追加（2026-01-14）
        ↓
2回目  FG-IR は既読なのでスキップ → 7.4 系が対象になったことに気づかない
```

実際に FG-IR-25-545 で再現させたところ、同じ CVE-2025-54821 が改訂前は `なし`、改訂後は `あり` になった。**6.4 の「対象の見逃しゼロ」に直接違反する。**

**対応**：

1. 既読の判定キーを **`FG-IR` から `FG-IR + 最終更新日` に変更**する
2. 最終更新日を知るため、**毎回 RSS 全件の CSAF を取得**する（`UrlFetchApp.fetchAll` で並行取得。50 件でも数秒）
3. 改訂を検知したら、**その FG-IR の古い行を台帳と処理済みシートから削除**してから入れ直す（`removeRowsFor_`）
4. 台帳の日付列を **`公開日`（初回公表日）から `最終更新日`（`current_release_date`）へ変更**する

*4 の理由*：この台帳は「やることリスト」であり、日付列の役割は「今月見るべきものはどれか」である。初回公表日で並べると、改訂で新たに対象になった件が何か月も前の日付として沈み、月次の集計から漏れる。FG-IR-25-545 は初回 2025-11 だが、実際に確認が必要になったのは改訂された 2026-01 である。初回公表日は処理済みシートに残すので情報は失わない。

*設計上の教訓*：**識別子が同じでも中身は変わる。** 「一度見たか」ではなく「今の版を見たか」で既読を判定する必要がある。1.8（脆弱性情報を持たないアドバイザリ）と同じく、**取得の記録と判断の記録を分けていなければ直せなかった**問題である。

## 2. 目的（v2 §1 を維持）

### 2.1 結論

**本ツールが自動化するのは「調べる作業」ではなく「対応しなくてよいと説得する作業」である。**

### 2.2 ゴール【一部変更】

1. **分母を機械的に確定する**（マネージャー起因をやめる）
2. **室長の3つの質問に答える材料を、公式情報から機械的に揃える**
   - 本当に影響がないと言い切れるのか
   - 攻撃されたら何が起きるのか
   - 他社・世間はどう対応しているのか
3. **判定結果と根拠を全件記録する**（次回、同種の CVE でゼロから調べない）

*3 について【変更】*：v2 は台帳に `human_verdict` / `human_note` / `approved_at` を持たせ、人の判断も同じシートに書き戻す設計だった。**v3 では台帳を「自動スクリーニングの出力」に限定し、人の判断は書かない。**

理由は 2 つある。台帳は毎回追記・並べ替えされる再生成可能なデータであり、人が書いた判断（再生成できない）を同居させると、並べ替えや列構成の変更で壊れる。もう一つは、レビューが指摘したとおり、確認結果の列があると「AI が使用中／未使用を判定してよい」という誤解を招くためである。

ゴール 3 は取り下げない。**人の判断の記録は、別シート「判断記録」として別フェーズで設計する**（6.3）。

### 2.3 業務背景

本業務の運用ルールを策定中で、10月から新運用を開始予定。**ツールが先ではなく、基準が先である。**

## 3. スコープ

### 3.1 対象製品【変更】

| # | 製品 | 資産シートでの表記 | 扱い |
|---|---|---|---|
| 1 | FortiOS（FortiGate 120G） | `FortiOS` | 全判定 |
| 2 | ~~FortiClient~~ | — | **対象外**【変更】 |
| 3 | ~~FortiClient EMS~~ | — | **対象外**【変更】 |
| 4 | macOS | — | KEV 掲載時のみ通知【未実装】 |
| 5 | Windows 11 | — | KEV 掲載時のみ通知【未実装】 |

**現時点で本ツールが判定するのは FortiOS のみである。**

*変更理由*：v2 §11.6 は「FortiClient / FortiClient EMS の判定軸」を**【未確認】**として残しており、「FortiOS と異なり、機能の使用有無ではなく配布バージョンのばらつきが問題になる可能性がある。アンラーニング未実施の領域」と書いていた。2026-08-12 に利用者へ確認し、**この 2 製品は本ツールの判定対象としない**ことが確定した。v2 §11.6 はこれで解消する。

したがって資産シートには FortiOS だけを登録する。初回運用の出力で FortiClientEMS / FortiClientWindows が `なし` になっていたのは**正しい挙動**であり、登録漏れではなかった（1.9 の注記）。

資産シートの `製品` 列は **Fortinet の表記に合わせる**。突合時に空白・ハイフン・大文字小文字は無視するが、迷ったら `listProductNames_()` を実行すると実際の表記が一覧できる。

**この決定が有効な前提**：FortiClient を端末に配布・更新する仕組み（EMS 経由の自動更新など）が別に存在し、脆弱性ごとの個別判断を必要としないこと。自社でバージョンを指定して適用しないと直らない運用であれば、macOS / Windows と同じ扱い（KEV 掲載時のみ通知）に格上げする必要がある。10 月の新運用策定で確認する。

### 3.2 作らないもの【確定】

| 作らないもの | 理由 |
|---|---|
| 自社固有の適用手順の生成 | LLM が自社環境を知らない。誤情報リスクが高い |
| 台帳の自動取得（Jamf/Intune API） | 認証・権限設計に工数を要する。初期は手動で成立する |
| 誤判定からの自動学習 | 月数件の規模では学習効果が出ない |
| チーム共有機能・権限管理 | まず自分専用で使う |
| **AI による機能利用状況の判定** | **AI に機器設定も利用実態も渡していない。`使用中`／`未使用` を出力させない**（レビュー指摘8） |

**除外を解いているもの**：製品一般の確認コマンドの提示。適用手順は自社環境依存で検証できないが、確認コマンドは製品一般の知識であり、実行すれば正誤が判明する。実務で最も助かっている使い方を残す。

**「取得」と「見る」を分ける。** 報告が月次だからといって取得も月次にする必要はない。

*1 回の実行コスト（実測）*

| 項目 | 実測値 |
|---|---|
| リクエスト数 | 51 回（RSS 1 + CSAF 50） |
| 転送量 | 264 KB（CSAF 1 件あたり平均 5.3 KB） |
| 所要時間 | CSAF 1 件 171 ms。`fetchAll` の並行取得で全体 2〜3 秒 |
| GAS の上限に対する比率 | UrlFetch 20,000 回/日に対し **0.26%** |

日次で回しても上限の 0.26% であり、新着が無ければ数秒で終わる。頻度を落とす動機がコスト面には無い。

*頻度を落とすと何が起きるか*

**Fortinet の RSS は常に 50 件しか持たない。** 実測の公表ペースは次のとおり。

| 月 | 件数 |
|---|---|
| 2026-04 | 18 |
| 2026-05 | 12 |
| 2026-06 | 4 |
| 2026-07 | 11 |

平均 11 件／月、最大 18 件／月。**50 件枠は平均 4.5 か月分、最悪 2.8 か月分**しかない。

- 日次 … 枠に対して 4 か月以上の余裕
- 月次 … 1 か月分（11〜18 件）を確実に拾えるので成立するが、2〜3 か月止めると溢れる
- **溢れてもエラーは出ない。押し出されたアドバイザリは二度と流れてこない**

分母の網羅性が本ツールの第一目的である以上、この静かな欠落は許容できない。

**対応**：RSS 50 件のうち何件が処理済みシートに記録済みかを数え、**前回との「重なり」が無ければ警告する**（`warnIfFeedOverflowed_`）。

| 重なり | 判定 |
|---|---|
| 5 件以上 | 連続性あり。正常 |
| 1〜4 件 | 注意。実行間隔が空きすぎ |
| 0 件 | **警告。50 件以上が入れ替わっており、取りこぼしを自力で判断できない。PSIRT サイトを人が突き合わせる** |

## 5. データ設計

### 5.1 台帳シート【全面変更】

**1 行 = 1 つの CVE × 1 つの対象製品。** レビュー指摘の 16 列に、`公開日` を 1 列足した 17 列。

**採用基準は「対応を決めるのに要るか」だけである。**

| ブロック | # | 列 | 生成 | 内容 |
|---|---|---|---|---|
| **A. いつ・何の件か・関係あるか** | 1 | 最終更新日 | コード | Fortinet が最後に情報を変えた日（1.10） |
| | 2 | CVE | コード | 人が読める識別子 |
| | 3 | 自社影響 | **コード** | `あり` / `なし` / `要確認` |
| | 4 | CVSS | コード | `8.3（HIGH）` のように帯を併記 |
| | 5 | 対象サービス／製品 | コード | CSAF の `scores[].products` |
| **B. 何の脆弱性か** | 6 | 脆弱性名 | コード | `document.title`。正式名（英語） |
| | 7 | ユーザ影響 | AI | 攻撃されたら何が起きるかを 20〜30 字で |
| | 8 | 影響機能名 | AI | 実質の判断軸。製品名は書かない |
| **C. なぜそう判定したか** | 9 | 判定根拠 | **コード** | 「〜のため」で終わる 1 行 |
| **D. 何をするか** | 10 | 利用有無の確認方法 | AI | `あり` の行のみ |
| | 11 | 対応 | **コード** | 更新先。`あり` と `要確認` のみ |
| **E. 出典** | 12 | Fortinetアドバイザリ | コード | `FG-IR-26-150` と表示し URL を貼る |

**左 5 列を固定表示にする**（`setFrozenColumns(5)`）。

*B ブロックは「総論 → 概論」の順*：正式名（脆弱性名）→ ざっくり何が起きるか（ユーザ影響）→ だからどの機能か（影響機能名）。人は全体像を掴んでから細部を読むほうが理解しやすい。

#### 判定根拠は「〜のため」の 1 行に収める【変更】

初版は根拠にバージョン番号を並べていたが、長すぎて読まれない。

| | 変更前 | 変更後 |
|---|---|---|
| `あり` | 利用中のバージョン「FortiOS 7.4.11」は対象に含まれます。 | **利用中のバージョンが対象のため** |
| `なし` | 利用中のバージョン「FortiOS 7.4.11」は対象に含まれません。（影響範囲：7.6.0、7.4.0〜7.4.7、7.2 系すべて、7.0 系すべて、6.4 系すべて） | **7.4 系の影響は 7.4.0〜7.4.7 までのため** |
| `要確認` | このアドバイザリの CSAF には脆弱性情報（vulnerabilities）が含まれていません。Linux Kernel や npm パッケージなど…（3 文） | **この情報元だけでは自社への影響を自動判定できません。アドバイザリを人が読んで判定してください。** |

`なし` の根拠では、**自社が使っている系列に対応する範囲だけ**を示す（`branchRange_`）。7.4.11 の利用者にとって 7.0 系や 6.4 系の範囲は読む理由がない。全範囲はアドバイザリのリンクから 1 クリックで辿れる。

#### `対応` は「何をするか」を先に言う【変更】

| 変更前 | 変更後 |
|---|---|
| 7.4 系に修正版なし → 7.6.5 以上に移行 | **7.6.5 以上に更新が必要（7.4 系に修正版なし）** |

行動を先頭に置き、理由を括弧に回す。

#### 17 列から 12 列に削った根拠【実データで確認】

初版の 17 列は「レビューが求めた項目」を並べたものだった。実際に出力してみると、**判断に使われない列が情報量の大半を占めていた**。

| 削った列 | 実データ | 判断 |
|---|---|---|
| 深刻度 | **56/56 行**が CVSS の帯と一致（CRITICAL≧9.0 / HIGH≧7.0 / MEDIUM≧4.0） | CVSS の関数。二重に持つ意味がない |
| 無認証リモート | 対象 10 行が**すべて「いいえ」**。「はい」の 20 行はすべて対象外 | 対応する行の中で値が割れない。かつ行き先（優先度判定）が 6.3-1 で保留中 |
| 自社利用バージョン | 値は `FortiOS 7.4.6` の**1 種類のみ**。かつ判定根拠に **10/10** で再掲 | 資産シートの転記であり、根拠の文中にもある |
| 脆弱性の影響バージョン | 対象 10 行で**計 44 行**（平均 4.4 行）。根拠が該当範囲を **10/10** で名指し | 全範囲は検証材料であって判断材料ではない。該当した 1 本だけあればよい |
| 対応方針 | 「7.4.9 以上へアップグレードしてください」＝ 修正バージョンの訳文 | 修正バージョンと同義。日本語化はコードでできる（`jpFix_`） |

**無認証リモートについて**：これは BOD 26-04 の「自動化された攻撃が可能か」の入力であり、本来は捨てたくない指標である。しかし**その優先度判定自体が 6.3-1 で保留中**であり、行き先のない列だった。v5 の `優先度` を削除したのと同じ理由（入力が揃っていない判定は列にしない）が、ここにも当てはまる。対応基準が承認された時点で復活させる。値は `isUnauthRemote_` で計算し続けており、列に出していないだけである。

**情報量の実測**（1 行あたりのセル文字数）

| | 修正前 | 修正後 |
|---|---|---|
| 対象（AI 列を除く） | 337 文字 | **261 文字** |
| 対象外 | 469 文字 | **234 文字** |

対象外の削減幅が大きいのは、**保有していない製品の修正指示を出すのをやめた**ためである。`対応` 列は `あり` と `要確認` にしか出さない。対象外 81 行がそれぞれ 5〜10 行の修正指示を抱えていたのが、情報量の最大の発生源だった。

**落とした情報は消えていない。** バージョンの根拠は `判定根拠` の 1 文に、修正指示は `対応` に日本語で入る。

#### 列順の根拠

- **1 列目を `自社影響` にした**。実測で 100 行中 81 行が `なし` であり、シートを開いて最初にする操作は絞り込みである
- **2 列目を `公開日` にした**。もう一つの軸が「今月の分か」であり、月次サマリの分母がここから出る
- **左から 4 列を固定表示にする**（`setFrozenColumns(4)`）。右側の説明列を読むとき、どの製品のどの CVE かを見失わないため

*レビュー指摘12（16列の並び）との差*：レビューは `対象サービス／製品` を 1 列目としていた。その意図は「何の機器の脆弱性か一目で分からない」の解消であり、**製品列を左側に置くという要求は満たしている**（3 列目）。そのうえで、実際に出力してみると最初の操作が製品の確認ではなく `あり` への絞り込みだったため、判定と公開日を先に置いた。

**削除した列**：取得日時 / 優先度 / CWE / CVSSベクター / 影響機能（重複）/ 何が起きるか（英語原文）/ 緩和策（独立列として）/ 自社該当バージョン / URL / 判定AI / FG-IR

#### `公開日` を残した理由【レビュー指摘11から外れる】

レビューは `公開日` を削除としているが、残した。**本ツールの第一のゴールが「分母を機械的に確定する」ことだからである。**

月次サマリの「今月 Fortinet から公表：N 件 / うち自社製品が対象：M 件」は、公開日がなければ計算できない。また RSS の 50 件枠には FG-IR-24-257 から FG-IR-26-154 まで 2 年分が混在しており、公開日がないと今月分を切り出せない。実際、初回実行の台帳には 2025/03/11 から 2026/07/14 までが混在した。

v3 初版では右端の参照情報として置いたが、**2 列目に移した**。集計の軸である以上、参照情報ではなく操作の軸だったためである。

*`取得日時` は削除した*。判断にも集計にも使わない。

#### 列数が減る移行の注意【実装済み】

v5 の 24 列から v6 の 17 列へ減るため、見出しを上書きするだけでは 18 列目以降に v5 の見出し（`CWE` / `CVSSベクター` / `影響機能` / `何が起きるか` / `影響バージョン` / `URL` / `判定AI`）が残る。`migrateLedgerHeaders()` で余剰列を `deleteColumns` する。初回実行時にこの取りこぼしが発生した。

### 5.1b 台帳に載せる行を、自社製品に絞る【変更】

**台帳には、資産シートに登録した製品の行と、製品を特定できなかった行だけを書く。**

実測で、50 アドバイザリは 100 行に展開されるが、そのうち **82 行は自社が使っていない製品**（FortiProxy / FortiPAM / FortiSandbox / FortiSOAR など 36 種）だった。スコープが FortiOS のみになった以上、これらは読む理由がない。

| | 行数 |
|---|---|
| 展開した全行 | 100 |
| **台帳に載せる** | **18**（対象 13 / 要確認 3 / 対象外 2） |
| 台帳に載せない | 82 |

*自社製品の `なし` は残す*。「利用中の 7.4.6 は影響する範囲（7.6.0〜7.6.4）に含まれていません」は、**対応不要と言い切る根拠**そのものであり、月次報告の主要部分になる（7.1）。捨てるのは「そもそも使っていない製品」の行だけである。

*製品を特定できなかった行も残す*。1.8 の「CSAF に脆弱性情報が無いアドバイザリ」は製品が空になるが、人が読まないと判断できないため必ず表に出す。

### 5.1b-2 古い「対象外」だけを台帳から落とす【変更】

RSS は直近 4 か月ほどの公表分を保持しており（実測 50 件中 45 件が 2026-04〜07）、初回実行では数か月前の分まで一度に入る。運用上は「直近 3 か月ぶんが見えていれば十分」という要望があった。

**ただし年齢で一律に切ってはいけない。** 実データで 3 か月の一律カットを試したところ、次の 2 行が消えた。

| 最終更新日 | 判定 | CVE | 状態 |
|---|---|---|---|
| 2026-01-13 | **対象** | CVE-2025-31514 | FortiOS 7.4.11 は今も影響範囲内。未対応 |
| 2026-01-13 | **対象** | CVE-2025-54821 | 同上 |

**古いということは、その分だけ長く直していないという意味であり、消す理由にならない。** 6.4 の見逃しゼロに反する。

一方、実際に邪魔だったのは古い `なし` である。

```
2025-08-08  対象外  CVE-2025-25250  利用中の 7.4.11 は影響範囲外
```

**そこで `なし` にだけ期限を設ける**（`KEEP_OUT_OF_SCOPE_MONTHS = 3`）。

| 判定 | 古くても残すか | 理由 |
|---|---|---|
| `あり` | **残す** | 未対応の事実は古さで消えない |
| `要確認` | **残す** | 人が読まないと判断できない |
| `なし` | 3 か月で落とす | 対応不要の根拠は、その月の報告に使ったら役目を終える |

実測（資産 FortiOS 7.4.11）：**18 行 → 13 行**。落ちた 5 行はすべて `なし` で、`あり` は 1 行も減らない。

分母は壊れない。落とした行も処理済みシートには残る。

*`0` にすれば無制限に戻る。* 月次報告で過去の「対応不要」根拠を遡りたくなったら伸ばせばよい。

### 5.1c 処理済みシート【新規】

台帳から 82 行を外すと、**そのままでは 2 つ壊れる**。

1. **既読管理**：台帳のアドバイザリ列を既読の根拠にしていたため、他社製品だけのアドバイザリが毎回「新着」に戻り、取得枠を食い続ける
2. **分母**：「今月 Fortinet から公表：N 件」が数えられなくなる。本ツールの第一目的

これは 1.8 で直したのとまったく同じ失敗の型である。**取得した事実は、台帳に載せるかどうかと切り離して記録する。**

| 列 | 内容 |
|---|---|
| 最終更新日 | 月別集計の軸。**FG-IR と組で既読判定のキーになる**（1.10） |
| 初回公表日 | 脆弱性が最初に世に出た日。台帳には出さない |
| FG-IR | **既読判定はここを見る**（台帳ではなく） |
| タイトル | 何のアドバイザリだったか |
| 台帳の行数 | 0 なら自社製品を含まなかった |
| 対象製品 | そのアドバイザリが対象とした製品の一覧 |

`countByMonth()` で月別の「公表件数 / 台帳に記録した行数」を出す。これが月次サマリの分母になる。

*`対象製品` 列の使い道*：自社で使い始めた製品がここに出ていないかを、たまに眺める。資産シートの登録漏れ（1.9）に気づく手がかりになる。

*レビュー「新しいシートは作成しないでください」との関係*：レビューが禁じたのは**台帳を分割すること**（確認結果や対応履歴を別シートに持つこと）であり、その趣旨は守っている。処理済みシートは台帳の一部を切り出したものではなく、**取得処理の記録**である。台帳の 1 行は依然として「CVE × 製品」であり、分割していない。

### 5.2 資産シート

| 列 | 例 | 備考 |
|---|---|---|
| 製品 | `FortiOS` | Fortinet の表記に合わせる |
| バージョン | `7.4.5` | **手動更新。これが判定の基準になる** |
| 台数 | `2` | |
| インターネット公開 | `あり` | 将来の緊急度判定で使う |
| 備考 | `SSL-VPN 有効` | |

*v2 §4.1 からの変更*：`cpe_pattern` を削除（NVD 不使用のため）。`version_checked_at`（最終確認日）は**必要だが未実装**とする。自社バージョンの正が担当者の記憶にあり、台帳と実機のズレを誰も検出できない問題は解決していない（6.3）。

### 5.3 機能台帳シート【未実装】

v2 §4.2 で「本ツールの中核データ」としたもの。**v3 でも未実装である。**

現時点で判定できるのは「自社の製品・バージョンが影響範囲に含まれるか」までであり、「その機能を使っているか」は人が確認する。13 列目の `利用有無の確認方法` は、その確認を人が行うための材料を出す列である。

機能台帳が入ると、13 列目の確認結果を蓄積して `あり` をさらに絞り込めるようになる。その設計は 6.3 に送る。

## 6. 処理フロー と 判定ロジック

### 6.1 処理フロー【変更】

```
[1] 取得
    RSS から新着アドバイザリを取得（既知の FG-IR は除外）
    タイトルから CSAF の URL を組み立てて取得
        ↓
[2] 展開【コード】
    CSAF の vulnerabilities[] を 1 要素 = 1 行に展開
    → 1 アドバイザリが平均 1.94 行になる（実測 50 → 97）
        ↓
[3] 自社影響【コード・LLM 不使用】
    製品を資産シートと突合 → 保有していなければ 対象外
    自社バージョンを影響バージョンと数値比較 → 対象 / 対象外
    バージョン不明・表記を解釈できない → 要確認
        ↓
[4] 日本語化【LLM 使用・対象と要確認の行のみ】
    影響機能名 / ユーザ影響 / 確認方法（対応はコードで日本語化する）
        ↓
[5] 出力
    全行を台帳に記録し、自社影響順に並べ替え
    対象・要確認 → Slack
```

**v2 からの最重要の変更は [3] である。**

v5 は自社影響を AI にやらせていた。実測（台帳 30 行）では **30 行中 20 行が「未判定」**になっていた。AI_CHUNK_SIZE=10 の 3 チャンクのうち 2 チャンクが失敗し、そのチャンクの行は判定ごと落ちていた。判定は決定的な計算であり、AI に任せる理由がない。

v3 では **自社影響は必ずコードで確定する**。AI が全部落ちても、判定と根拠は台帳に残る。埋まらないのは日本語の説明欄だけであり、それは次回 `backfillAiColumns_()` が埋め直す。

副次的な効果として、**AI に渡す行が全体の 2 割以下になる**。実測では 97 行中、資産に該当する製品の行は 19 行（20%）、うち対象は 16 行だった。残る 81 行はコードだけで `なし` と確定する。トークン数が減り、チャンク失敗そのものが起きにくくなる。

### 6.2 自社影響の 3 分類【変更・レビュー指摘4を採用】

| 値 | 条件 | 通知 |
|---|---|---|
| `あり` | 自社が対象製品を保有し、**かつ**自社利用バージョンが影響範囲に含まれる | Slack + 台帳 |
| `なし` | 対象製品を保有していない、**または**利用バージョンが影響範囲外 | 台帳のみ |
| `要確認` | 製品は保有しているがバージョンが不明／表記を解釈できない／取得に失敗 | Slack + 台帳 |

**`あり` の意味を取り違えないこと。**

> 自社の製品・バージョンが影響範囲に含まれるため、影響機能の利用有無を確認する必要がある

これは、影響機能を実際に利用していることも、自社環境への影響が確定したことも意味しない。確認するのは人であり、その方法を 13 列目に出す。

#### v2 の 4 分類との関係

v2 は `act_now` / `act_scheduled` / `no_action` / `needs_review` の 4 分類だった。これは**捨てたのではなく、別の軸として分離した**。

| 軸 | 問い | 決めるのに必要なもの | 状態 |
|---|---|---|---|
| **自社影響**（v3で実装） | 見る必要があるか | 資産シートと CSAF | **今できる** |
| **対応区分**（v2の4分類） | どれだけ急いで対応するか | 機能台帳 + 対応基準の室長承認 | **どちらも未達** |

v2 は 2 つの軸を 1 列に混ぜていた。`act_now` を出すには「機能を使っているか」と「何日以内か」が要るが、前者は機能台帳がなく、後者は基準が未承認である。**入力が揃っていない判定を列として持つと、根拠のない値が入る。** 実際、v5 の台帳では `優先度` に「中」「低」が入っていたが、その基準はどこにも定義されていなかった。レビュー指摘9（優先度を削除）はこれを突いている。

対応区分は、機能台帳と対応基準が揃った時点で追加する。

v2 で設計に含めていたが、v3 では実装しないものを明示する。**忘れたのではなく、前提が揃っていないため保留している。**

### 6.4 合格基準（非対称）【確定】

## 7. 出力仕様

### 7.1 設計方針

**出力は「室長の3つの質問」に先回りして答える形式とする。**

| 質問 | 埋める材料 | 出所 | 状態 |
|---|---|---|---|
| 本当に影響がないと言い切れるのか | `判定根拠`（どのバージョンがどの範囲に入る／入らないか） | 資産 + CSAF | **実装済** |
| 攻撃されたら何が起きるのか | `ユーザ影響` | CSAF | **実装済** |
| 他社・世間はどう対応しているのか | KEV 掲載の有無、Fortinet が臨時公開したか | CISA / Fortinet | **未実装**（6.3-4） |

3 つ目は「他社の対応状況」そのものを取得できない。**KEV 掲載の有無とベンダーの公開区分（月次か臨時か）を、世間の緊急度の代理指標として使う。** これは公的機関とベンダー自身の判断であり、出典を示せる。

### 7.2 各行が答えること【レビュー §13 完成条件】

台帳の 1 行を見れば、次がすべて分かる状態にする。

| # | 分かること | 列 |
|---|---|---|
| 1 | 何の機器・ソフトウェアの脆弱性か | 3 対象サービス／製品 |
| 2 | どの CVE か | 4 CVE |
| 3 | どれくらい危ないか | 6 CVSS |
| 4 | 自社利用バージョンが影響範囲に含まれるか | 1, 7 |
| 5 | なぜ対象になったか | 7 判定根拠 |
| 6 | どの機能に影響するか | 8 影響機能名 |
| 7 | 悪用されると何が起きるか | 5 ユーザ影響 |
| 8 | 影響機能を使っているかどう確認するか | 10 確認方法 |
| 9 | 推奨される対応 | 11 対応 |
| 10 | 根拠となるアドバイザリ | 12 Fortinetアドバイザリ |

*レビュー §13 の「無認証・リモートから攻撃可能か」は列から外した*。理由は 5.1 のとおりで、対応する行の中で値が割れず、その値を使う優先度判定が保留中のためである。

実際の出力例（実データ・列順どおり）：

```
自社影響         : 対象
公開日           : 2025/10/14
対象サービス／製品 : FortiOS
脆弱性名         : Insertion of Sensitive 2FA Information in logs and debug command
CVE              : CVE-2025-31514
深刻度           : LOW（2.6）
判定根拠         : 利用中の 7.4.6 が影響する範囲（7.4 系すべて）に含まれています。
                   影響する機能を使用しているか調査が必要です。
影響機能名       : ログ・デバッグ出力
ユーザ影響           : （AI生成）
利用有無の確認方法 : （AI生成）
対応             : 7.4 系に修正版なし → 7.6.4 以上に移行
Fortinetアドバイザリ : FG-IR-24-452
```

対象外の行は判定根拠の 1 文で終わる。

```
自社影響         : 対象外
判定根拠         : 利用中の 7.4.6 は影響する範囲（7.6.0〜7.6.4）に含まれていません。
```
```
自社影響         : 対象外
判定根拠         : FortiSASE は自社で使用していません。
```

#### バージョン表記は生のまま出さない【変更】

CSAF の `>=7.4.0|<=7.4.8` という表記は、自分が対象かどうかを読み取るのに時間がかかる。人が読む形に直す。

| CSAF | 台帳 |
|---|---|
| `FortiOS >=7.4.0\|<=7.4.8` | `7.4.0〜7.4.8` |
| `FortiOS 7.4 all versions` | `7.4 系すべて` |
| `FortiOS 7.2.2 and above` | `7.2.2 以上` |

#### 「修正版なし」の移行先はベンダーが書いている【変更】

`Migrate to a fixed release` は「この系列に修正版はない」としか言っておらず、**どこへ上げればよいかが書かれていない**。ところが同じアドバイザリの他系列には、ベンダー自身が更新先を書いている。

```
FortiOS 7.6: Upgrade to 7.6.4 or above     ← ここから引く
FortiOS 7.4: Migrate to a fixed release    ← 自社の系列
```

自社系列より上で最も低い更新先を選び、`7.4 系に修正版なし → 7.6.4 以上に移行` と出す（`migrateTarget_`）。**推測ではなくベンダー記載の転記である。** 見つからない場合は移行先を書かない。

### 7.3 AI に出させないこと【レビュー指摘8を採用】

プロンプトで明示的に禁じている。

- **`使用中` / `未使用` の判定**：機器設定も利用実態も渡していないため判断できない
- **画面名・設定項目・確認コマンドの作文**：確証がない場合は「正確な確認手順を特定できません」と書かせる
- **アドバイザリに書かれていない被害の推測**
- **製品名を影響機能名として書くこと**：v5 の実データで `FortiSIEM` `FortiClient EMS` が影響機能名の欄に入っていた

確認方法は、次の書式ちょうどで書かせる。前置きを足させない。

```
下記の方法で影響する機能を使用しているか確認してください。
・【確認箇所】SSL-VPN の設定
・【コマンド】show vpn ssl settings
・【見るところ】status が enable なら使用しています
```

初版は前置きを「自社製品・バージョンが影響範囲に含まれます。影響機能の利用状況は現在の情報だけでは判断できないため、以下の方法で確認してください。」としていたが、**自社影響＝対象という列の値が既に同じことを言っており、冗長だった**。1 行に縮めた。

#### 禁止の強さを誤ると、列が空洞になる【初回実行で判明・修正済み】

初版のプロンプトは「画面名・設定項目名・コマンドを、確証がないまま作文しないでください」と書き、逃げ道として「正確な確認方法が分からない場合は『特定できません』と書いてください」を用意していた。

結果、**AI 生成に成功した全行がこう出力した。**

> …以下の方法で確認してください。**正確な確認手順を特定できません。Fortinet のドキュメントで確認してください。**

「以下の方法で」と言いながら何も示していない。禁止が強く、逃げ道が易しいと、AI は常に逃げる。レビュー指摘8が作らせたかった列が、そのまま空洞になった。

**これは §3.2 の判断と矛盾していた。** 設計上、確認コマンドは「製品一般の知識であり、実行すれば正誤が判明する」という理由でスコープ内に残していた。プロンプトだけが過剰に締めていた。

修正した点：

- **参照系コマンド（`show` / `get` / `diagnose`）は公開知識なので書いてよい**と明示する。変更系（`set` / `execute`）は引き続き禁止
- 出力書式を【確認箇所】【コマンド】【見るところ】に固定し、書くべき粒度を示す
- SSL-VPN を例に、期待する出力を丸ごと 1 件見せる
- 逃げ道を**「影響機能名が『不明・要確認』になった行だけ」に限定**する
- コマンドに自信がないときは【コマンド】行だけ省き、【確認箇所】と【見るところ】は書かせる

禁止すべきは「自社固有の」設定名の捏造であって、製品標準の設定名やコマンドではない。この線引きをプロンプトの文面に落とし込めていなかった。

### 7.4 Slack 通知【変更】

**通知の仕事は 3 つだけ**：何件あるか／どれが一番まずいか／どこを見るか。

初版は 1 件あたり 7 行を平文で流していた。

```
:warning: FortiOS / CVE-2026-71408 UI DoS attack
　対象 / CVSS 5
　利用中のバージョン「FortiOS 7.4.11」は対象に含まれます。
　影響機能: GUI（管理画面）
　管理画面の応答が停止し管理操作できなくなる
　下記の方法で影響する機能を使用しているか確認してください。
・【確認箇所】管理画面（GUI）アクセス設定
・【コマンド】show system global
・【見るところ】admin-sport または admin-port の設定項目
　対応: 7.4 系に修正版なし → 7.6.7 以上に移行
```

**問題は情報量ではなく、すべてが同じ太さで並んでいること**である。目が滑り、どこから読むべきか分からない。加えて確認コマンドと判定根拠は台帳の仕事であり、通知に載せる理由がない。

**Block Kit で 1 件を 3 ブロックに分ける。**

| 順 | 内容 | 見え方 |
|---|---|---|
| 1 | 何が起きるか（`ユーザ影響`） | **太字** |
| 2 | CVE・CVSS・影響機能 | 小さい灰色（context ブロック） |
| 3 | どうするか（`対応`） | 🔧 付きの通常文字 |

**「何が起きるか → 何の件か → どうするか」**の順。太字だけ追えば全体が掴め、気になった行だけ灰色を読む。結論（対応）は最後に置く。

```
🚨 Fortinet 影響あり 2件 ／ 要確認 1件

無線機器の通信処理を乗っ取られる
  影響あり · CVE-2025-53844 · CVSS 8.3 · wireless controller（CAPWAP）
🔧 7.4.9 以上に更新が必要
────────────────────────────────────────────
管理画面の応答が停止し管理操作できなくなる
  影響あり · CVE-2026-71408 · CVSS 5 · GUI（管理画面）
🔧 7.6.7 以上に更新が必要（7.4 系に修正版なし）
────────────────────────────────────────────
詳細不明のため自社環境への影響は要確認
  要確認 · CVE-2026-31431 · 不明・要確認
────────────────────────────────────────────
影響なし 2件は台帳のみ · 台帳を開く（確認コマンド・判定根拠はこちら）
```

決めたこと：

- **CVSS の高い順に並べる。** 1 行目が「一番まずいもの」になる
- **確認コマンド・判定根拠は載せない。** 台帳へのリンクに置き換える
- **アイコンは最大 CVSS で決める**（7.0 以上は 🚨、それ以外は ⚠️）
- **5 件を超えたら「ほか N 件」にまとめる**（`SLACK_MAX_ITEMS`）
- **影響ありが 0 件なら通知しない**（`NOTIFY_WHEN_NO_HITS = false`）。日次実行では静かなほうがよい
- `text` フィールドにも要約を入れる。モバイルのプレビューと通知バナーはこれを読む

## 9. 完成の定義

### 9.1 検証方法【確定】

シャドウ運用。通知が来たら従来どおり人手でも調査し、判定が一致したかを毎回記録する。統計的な精度は主張しない。

**分母の一致**：ツールが検出したアドバイザリ件数と、PSIRT サイトを人が数えた件数が一致するか。ここがズレると全体が信用されない。

### 9.2 コード側の検証【実施済】

| 検証 | 結果 |
|---|---|
| CSAF URL の導出 | RSS 50 件すべてで成功（`testCsafUrls()`） |
| バージョン比較 | 実表記 7 種類を含む 17 ケースすべて期待どおり（`testVersion()`） |
| 自社影響の全件実行 | 100 行を判定。対象 16 / 要確認 3 / 対象外 81 |
| **分母の一致** | **台帳に現れるアドバイザリ 50 / RSS 全件 50。** 1.8 の修正前は 47/50 で 3 件欠落していた |

## 付録：設計上の判断原則

| 原則 | 内容 |
|---|---|
| 公式情報のみを出力する | 公式に記載のない内容を LLM に生成させない |
| **決定的な処理と自然言語処理を分ける** | **バージョン比較・製品突合・自社影響はコード。機能名の抽出と平易化のみ LLM。判定を LLM に依存させると、LLM が落ちたとき判定ごと消える** |
| 安全側に倒す | 要確認なものは `要確認` として正直に出す。`なし` に丸めない |
| 縦に薄く1本通す | 範囲を広げるより、1本を最後まで通す |
| 既存の構成に載せる | GAS + スプレッドシート + Slack + Googleドキュメント |
| 判断ではなく、判断の根拠を残す | 結論は議事録に残る。残らないのは根拠である |
| 対応しない判断を支える | ツールの価値は「やれ」と言うことではなく「やらなくてよい」と言い切る材料を揃えることにある |
| **入力が揃っていない判定は列にしない** | **根拠のない値が入るくらいなら、列ごと持たない（v5 の `優先度` の教訓）** |
