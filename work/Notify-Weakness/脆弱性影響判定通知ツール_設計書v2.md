# 設計書v2：脆弱性 影響判定・通知ツール

**文書の位置づけ**
別エージェントが設計を具体化するための入力。v1に対し、現行業務のアンラーニング（2026年8月実施）の結果を反映して骨格を変更した。

**記載ルール**
- 【確定】合意済み。変更する場合は理由を明示すること
- 【変更】v1から変えた箇所。理由を併記している
- 【未検証】前提として置いているが、一次情報・実データで確認していない。**確認を最優先タスクとする**
- 【未決】まだ決めていない。具体化フェーズで決める

---

## 1. 目的

### 1.1 結論

**本ツールが自動化するのは「調べる作業」ではなく「対応しなくてよいと説得する作業」である。**

v1は検知・突合・バージョン比較（工程1〜5）の自動化を主眼に置いていた。しかし実測の結果、そこには時間を使っていない。時間を食っているのは、影響内容の理解と、上長を納得させる根拠集めである。狙う場所を移す。

### 1.2 現状業務（アンラーニング結果）

直近1件（FortiOS、6CVE、対応不要で決着）を時系列で再現して得た事実。v1はこの実態を把握しないまま書かれていた。

**判明した事実**

| # | 事実 | v1の記述とのズレ |
|---|---|---|
| 1 | 脆弱性の存在はマネージャーから記事URLで渡される | v1は工程1を「負荷:小」とし、自力検知の欠落を課題として扱っていない |
| 2 | 「今月6件」の分母は、渡された記事1本に載っていた件数 | 網羅性が担保されていない。室長には月次の全体像として報告されている |
| 3 | 判定の実質的な軸は**該当機能を使っているか**。バージョン該当でも機能未使用なら対応不要と判断 | v1の判定ロジックはバージョン比較のみ。実務の判断を再現できない |
| 4 | 機能の使用有無は、LLMに確認コマンドを聞き、CLIで実行し、出力をLLMに読ませて判断している | v1は「LLMに判断させない」設計。実務は既に判断をLLMに渡している |
| 5 | 自社バージョンは記憶から取り出している | 台帳の`current_version`を埋める根拠が存在しない |
| 6 | 判定過程はメモ帳に書き、提出後に消える。議事録には結論5行だけが残る | v1の「判断がどこにも残っていない」は不正確。残っていないのは**根拠** |
| 7 | 報告単位は月次集計（Googleドキュメントの定例アジェンダ5行）。承認者は室長 | v1はCVE単位の週次Slack通知。転記作業が消えない |
| 8 | 半日以上／月（6件分）。うち大半は影響の理解と説得材料の収集 | v1の「1件60分」は単位が実態と異なる |
| 9 | 対応要否の基準が存在しない。「大丈夫と言える材料がない」ため対応した経験がある | v1に基準の概念がない |
| 10 | 更新は全社通信断・事前告知・検証環境なしの本番適用。承認から完了まで1〜3ヶ月 | v1は適用フェーズを考慮していない。短い期限は書けない |
| 11 | 緩和策（設定変更で危険を下げる）を選択肢として持てていない | v1にない。中間の選択肢がないため判断が重い |
| 12 | macOS / Windows は個別調査していない（月次更新で配布済み） | v1はこの2製品をスコープに含めている。存在しない業務の自動化になる |

**洗い出した面倒（23件）**

*気づく*
1. 公表に自力で気づけず、マネージャー起因で動き出す
2. 網羅できているか誰も検証できない

*読む*
3. 記事からCVE番号を拾う
4. どのサイトが正か毎回Googleで探す
5. 1本のアドバイザリに複数CVEがあり、CVEと影響バージョン表を対応付ける

*自社に当てる*
6. 自社バージョンを記憶から取り出す
7. 機能の使用有無を確認するコマンドを毎回LLMに聞く
8. CLIにログインして実行する
9. 出力の読み方をLLMに聞き直す
10. 判定結果をメモ帳に書く

*まとめる*
11. 6件を集計して「うち影響3件」の形に直す
12. 5行に要約してGoogleドキュメントに転記する

*説得する*
13. 「本当に影響がないと言い切れるのか」に答える材料を集める
14. 「攻撃されたら何が起きるか」を英語アドバイザリから読み取る
15. 「他社はどうしているか」を調べる
16. 基準がないため、不要と言い切れず対応してしまう

*対応する*
17. 更新手順を毎回調査する
18. 手順書を作る
19. 夜間・休日の日程調整と全社告知
20. 検証環境がないまま本番適用する
21. 承認から適用完了まで1〜3ヶ月かかる
22. 緩和策という中間の選択肢がない

*残す*
23. 根拠がメモ帳と共に消え、次回参照できない

### 1.3 本質的な問題

**対応の実コストが高いのに、対応しない判断を正当化する基準がない。** だから証明責任が担当者個人に来て、証明できず対応する。半日の大半が説得材料の収集に消えているのはこの構造による。

副次的な問題として、分母（その月に自社製品で公表された脆弱性の全体）が外部依存で、網羅性が誰にも検証できない。

### 1.4 ゴール【変更】

1. **分母を機械的に確定する**（マネージャー起因をやめる）
2. **室長の3つの質問に答える材料を、公式情報から機械的に揃える**
   - 本当に影響がないと言い切れるのか
   - 攻撃されたら何が起きるのか
   - 他社・世間はどう対応しているのか
3. **判定結果と根拠を全件記録する**（次回、同種のCVEでゼロから調べない）

*変更理由*：v1のゴール「工程1〜8の自動化」は、時間を使っていない工程を含んでいた。実測にもとづき、効く3点に絞る。

### 1.5 業務背景

本業務の運用ルールを策定中で、10月から新運用を開始予定。本ツールはルールの一部として組み込む。**ツールが先ではなく、基準（6.2）が先である。**

## 2. スコープ

### 2.1 対象製品【変更】

| # | 製品 | 社内での役割 | 扱い |
|---|---|---|---|
| 1 | FortiOS（FortiGate 120G） | 全社インターネット出口・VPN | 全判定 |
| 2 | FortiClient | 端末側VPNクライアント | 全判定 |
| 3 | FortiClient EMS | FortiClient 管理サーバー | 全判定 |
| 4 | macOS | Jamf Pro 管理 | **KEV掲載時のみ通知** |
| 5 | Windows 11 | Intune 管理 | **KEV掲載時のみ通知** |

*変更理由*：macOS / Windows は月次の定期更新で配布済み。v1の除外基準「自社でバージョンを適用しなければ修正されない製品」を当てると、ブラウザと同じ側に入る。この2製品について問うべきは「該当するか」ではなく**「今月の定期更新を待つか、前倒しするか」**であり、その判断が要るのはKEV掲載時に限られる。KEVフィードのフィルタだけで実装でき、既存業務も壊さない。

### 2.2 作らないもの【確定】

| 作らないもの | 理由 |
|---|---|
| 自社固有の適用手順の生成（Jamf/Intuneでの当て方、夜間作業手順） | LLMが自社環境を知らない。誤情報リスクが高い |
| 台帳の自動取得（Jamf Pro / Intune API連携） | 認証・権限設計に工数を要する。初期は手動台帳で成立する |
| 誤判定からの自動学習 | 月数件の規模では学習効果が出ない |
| チーム共有機能・権限管理 | まず自分専用で使う |

**v1から除外を解いたもの**：製品一般の確認コマンドの提示。v1は「適用手順の生成」と一括して禁止していたが、この2つは別物である。適用手順は自社環境依存で検証できないのに対し、確認コマンドは製品一般の知識であり、実行すれば正誤が判明する。実務で最も助かっている使い方を残す。

### 2.3 利用者【確定】

第1フェーズは作成者本人のみ。

```
          └─────────┬─────────┘   │ ・機能台帳    │
                    │             │ ・判定ログ    │
                    │             └──────────────┘
                    ├──▶ Vertex AI (Gemini) : 影響機能の抽出／平易化

```

*変更理由*：出力先をSlack単独からGoogleドキュメント併用に変えた。実際の承認の場は定例MTGで画面に映すGoogleドキュメントであり、Slackに通知が来ても5行への転記作業が残るため。GASはDocumentAppでGoogleドキュメントを直接操作できる。

### 3.2 データソース【変更】

| ソース | 用途 | 形式 |
|---|---|---|
| **Fortinet PSIRT** | **影響機能、緩和策（Workarounds）、修正版、公開日** | **RSS / HTML** |
| NVD API | CVE本体、CPE、影響バージョン範囲、CVSS | JSON |
| CISA KEV | 悪用が確認されたCVEのカタログ | JSON |

*変更理由*：v1はベンダーPSIRTを「実装形式が製品ごとに分かれる」として不採用にしていた。しかし判断に必要な情報（どの機能の脆弱性か、更新せずに危険を下げる方法があるか）はPSIRTにしかなく、NVDにはない。またFortinetはRSSフィードを公開しており、公開日も定まっているため、この懸念は少なくともFortinetには当たらない。対象を実質Forti系3製品に絞ったことで、実装形式の分岐も発生しない。

- PSIRT一覧：https://www.fortiguard.com/psirt
- RSSフィード：https://www.fortiguard.com/rss/ir.xml
- 公開サイクル：high以下は毎月第2火曜、criticalは随時の臨時公開（出典：https://community.fortinet.com/fortiguard-23/psirt-note-fortinet-psirt-and-monthly-psirt-advisories-94244 ）

**この公開サイクルが分母を確定させる。** 月次の定例で「今月Fortinetから公表されたのは全部でN件、うち自社該当はM件」と言い切れる状態になる。

### 3.3 実行頻度【変更】

| 種別 | 頻度 | 状態 |
|---|---|---|
| 定期バッチ | 週次 | 【確定】 |
| 月次サマリ生成 | 定例MTGの前営業日 | 【確定・追加】 |
| KEV掲載・緊急該当時の即時通知 | 日次ポーリング | 【変更】 |

*変更理由*：v1は即時通知を短間隔ポーリングで検討していたが、承認から適用まで1〜3ヶ月かかる現実に対し、数時間の速報性は意味を持たない。日次で足りる。工数も浮く。

## 5. 処理フロー

```
[1] 取得
    Fortinet PSIRT RSS から新規アドバイザリを取得（分母の確定）
    NVD API から該当CVEの CPE / バージョン範囲 / CVSS を取得
    CISA KEV の差分を取得
        ↓
[2] 一次フィルタ
    アドバイザリの対象製品と台帳を突合
    macOS / Windows は KEV 掲載時のみ通過させる
        ↓
[3] バージョン判定【コードで実行・LLM不使用】
    セマンティックバージョンとして数値比較
    → in_range / out_of_range / unknown
        ↓
[4] 影響機能の抽出【LLM使用】
    アドバイザリ本文から、影響を受ける機能名を抽出させる
    ※ 本文に書かれた機能名をそのまま返させる。推測させない
        ↓
[5] 機能突合【コードで実行・LLM不使用】
    抽出した機能名を機能台帳の feature_names と突合
    → in_use / not_in_use / unknown
        ↓
[6] 判定と期限算出【コードで実行】
    6.1 の表に従い verdict と due_date を決める
        ↓
[7] 説得材料の生成【LLM使用】
    impact_plain（攻撃されたら何が起きるか）を公式記載の範囲で3行に
    workaround をアドバイザリの Workarounds から抽出
        ↓
[8] 出力
    全件を判定ログに記録
    act_now → Slack即時通知
    全件 → 月次サマリとしてGoogleドキュメントに草案生成
```

**設計上の核心（v1から拡張）**

v1は「バージョン比較はコード、自然言語処理はLLM」を原則としていた。v2ではこれを機能判定にも適用する。**機能名の抽出はLLM（自然言語）、使用有無の判定はコード（台帳との突合）**に分ける。LLMに「使っているか」を判断させない。

## 6. 判定ロジック仕様

### 6.1 4分類【変更】

| verdict | 条件 | 通知 |
|---|---|---|
| `act_now` | バージョン該当 かつ 機能使用中 かつ 6.2の緊急条件を満たす | Slack即時 + 月次 |
| `act_scheduled` | バージョン該当 かつ 機能使用中 だが緊急条件を満たさない | 月次 |
| `no_action` | バージョン範囲外、または該当機能を使用していない | 月次（件数と根拠のみ） |
| `needs_review` | バージョンまたは機能の判定が `unknown` | Slack + 月次 |

*変更理由*：v1の3分類（affected / not_affected / needs_review）には期限の概念がなく、「該当するが次回定期更新でよい」を表現できない。この中間がないことが、対応要否の判断を重くしている根本原因である。

**`no_action` も月次に出す。** v1は`not_affected`を通知していなかったが、室長への報告は「今月N件中、対応不要がM件」という形であり、対応不要の件数と根拠こそが報告の主要部分である。

### 6.2 対応基準【新規・要承認】

**CISA BOD 26-04 の4条件を骨格として採用する。**

採用理由：担当者が基準の妥当性を自分で証明しなくて済むため。「私がこう決めました」は説明責任が担当者に返るが、「米国CISAが政府機関に課している基準です」は議論の対象が変わる。現状の「大丈夫と言える材料がない」問題への直接の解答になる。

- 公式：https://www.cisa.gov/news-events/directives/bod-26-04-prioritizing-security-updates-based-risk
- 実装ガイダンス：https://www.cisa.gov/news-events/directives/bod-26-04-implementation-guidance-prioritizing-security-updates-based-risk

4条件：インターネットに公開されているか／KEVに掲載されているか／自動化された攻撃が可能か／技術的影響が大きいか。

**社内期限【未決・室長承認が必要】**

| 該当条件 | 対応期限 | 対応の定義 |
|---|---|---|
| 4条件すべて | 3日以内 | **緩和策の適用でよい**。更新は別途スケジュール |
| KEV掲載 + インターネット公開 | 14日以内 | 緩和策または更新 |
| 上記以外で機能使用中 | 次回定期メンテナンス枠 | 更新 |
| 機能未使用 / バージョン範囲外 | 対応不要 | 記録のみ |

**期限を「更新」ではなく「対応（更新または緩和）」に対して切ることが要点である。** 現状、承認から適用完了まで1〜3ヶ月かかるため、更新に対して3日や14日の期限を設定すると初日から破綻する。緩和策を正式な対応手段として基準に組み込むことで、期限が守れる形になる。

**あわせて決めること【未決】**：緊急枠の事前確保。毎月◯曜◯時を予備メンテナンス枠として先に押さえておかないと、期限は絵に描いた餅になる。基準とセットで室長の承認を取る。

### 6.3 合格基準（非対称）【確定】

- `act_now` / `act_scheduled` の見逃し → **ゼロが必須**
- 過検知 → 許容する
- `needs_review` の件数 → 改善指標として記録する

## 7. 出力仕様

### 7.1 設計方針【変更】

**出力は「室長の3つの質問」に先回りして答える形式とする。**

実際に定例で問われた3点：

| 質問 | 埋める材料 | 出所 |
|---|---|---|
| 本当に影響がないと言い切れるのか | 機能台帳の`in_use=no` + `verified_by`（確認に使ったコマンドと出力） | 自社台帳 |
| 攻撃されたら何が起きるのか | `impact_plain`（公式記載の平易化） | PSIRT / NVD |
| 他社・世間はどう対応しているのか | KEV掲載の有無、CVSS、Fortinetが臨時公開したか（=ベンダー自身の緊急度評価） | CISA / Fortinet |

3つ目は「他社の対応状況」そのものを取得できない。**KEV掲載の有無とベンダーの公開区分（月次 or 臨時）を、世間の緊急度の代理指標として使う。** これは公的機関とベンダー自身の判断であり、出典を示せる。

### 7.2 月次サマリ（Googleドキュメント）【新規】

定例アジェンダに草案として自動生成する。人はこれを確認し、必要なら手直しして定例で映す。転記作業を消す。

### 7.3 Slack即時通知【変更】

`act_now` と `needs_review` のみ。日常的な通知は流さない。

*変更理由*：v1は`affected`全件をSlackに流す設計だったが、報告の実態は月次であり、逐次通知は読む負担を増やすだけで承認プロセスに乗らない。

### 7.4 `needs_review` の処理【確定】

Slack通知し、判定ログに行を立てる。人が`human_verdict` / `human_note`に判断と根拠を書き戻す。自動学習はしない。

## 9. 完成の定義

### 9.1 検証方法【確定】

シャドウ運用。通知が来たら従来どおり人手でも調査し、判定が一致したかを毎回記録する。バックテストは採用しない。検証できる件数は数件程度になる見込みで、統計的な精度は主張しない。

**v2で追加する検証観点**：分母の一致。ツールが検出したアドバイザリ件数と、PSIRTサイトを人が数えた件数が一致するか。ここがズレると全体が信用されない。

### 9.2 成果指標（発表用）【変更】

| 指標 | 現状 | 目標 | 根拠の性質 |
|---|---|---|---|
| 月あたり所要時間 | 4時間以上 | 1時間以内 | 実測（2026年8月・6件） |
| 分母の網羅性 | 外部依存（渡された記事のみ） | 公式RSS全件 | 事実 |
| 判断根拠の記録率 | 0%（メモ帳と共に消える） | 100% | 事実 |
| 対応要否の基準 | なし | 明文化・室長承認済み | 事実 |
| 中間の選択肢（緩和策） | なし | 判定結果に自動添付 | 事実 |

*変更理由*：v1の「1件60分→5分」は単位が実態と異なる。実際は月次バッチで半日以上。年間削減は概ね6人日で、劇的ではない。**発表の主張は時間削減ではなく、網羅性と判断根拠の保存に置く。**

## 11. 未決事項・要検証（**最優先で潰す**）

### 11.1 PSIRTから影響機能とWorkaroundsを機械的に取れるか【未検証・最優先】

**v2の設計はこれに依存している。** RSSにタイトルとURLしかない場合、詳細ページのHTML構造に依存した抽出が必要になる。構造が安定していなければ、LLMにページ全文を渡して抽出させる方式に切り替える。

**検証タスク**：過去のFortiOSアドバイザリを5件取得し、RSSの項目とHTMLの構造を確認する。3時間で区切る。

### 11.2 機能台帳の粒度【未決】

アドバイザリの機能名表記がどの程度ゆれるか、実データを見てから`feature_names`の設計を決める。粒度が細かすぎると突合が外れ、粗すぎると過検知になる。

### 11.3 対応基準の社内承認【未決・ツールより先】

6.2の期限表と緊急メンテナンス枠を室長に承認させる。**ここが通らないとツールを作っても判断が変わらない。** 10月の新運用策定に合わせる。

### 11.4 NVDのCPE付与遅延【未検証】

PSIRTを一次ソースにしたことで、NVDの遅延は速報性に影響しなくなった可能性が高い。優先度は下げる。

### 11.5 GAS 6分制限への分割設計【未決】

実データ量を見てから決める。

### 11.6 FortiClient / FortiClient EMS の判定軸【未確認】

FortiOSと異なり、機能の使用有無ではなく配布バージョンのばらつきが問題になる可能性がある。アンラーニング未実施の領域。

## 付録：設計上の判断原則

| 原則 | 内容 |
|---|---|
| 公式情報のみを出力する | 公式に記載のない内容をLLMに生成させない |
| 決定的な処理と自然言語処理を分ける | バージョン比較と機能突合はコード、機能名の抽出と平易化はLLM |
| 安全側に倒す | 判定不能なものは`needs_review`として正直に出す |
| 縦に薄く1本通す | 範囲を広げるより、1本を最後まで通す |
| 既存の構成に載せる | GAS + スプレッドシート + Slack + Googleドキュメント |
| **判断ではなく、判断の根拠を残す** | **結論は議事録に残る。残らないのは根拠である。根拠こそ次回の参照元になる** |
| **対応しない判断を支える** | **対応が高くつく以上、ツールの価値は「やれ」と言うことではなく「やらなくてよい」と言い切る材料を揃えることにある** |
