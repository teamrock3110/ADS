## 1. 何を作ったか（30 秒）

既存の「NW機器 脆弱性ウォッチャー」（Google スプレッドシート + Apps Script）に、
**macOS リリース監視モジュール**を追加した。

毎朝 Apple Security Releases から macOS のリリースを取り、
**「早めに当てるか・定期更新まで待てるか」**を固定ルールで判定して Slack へ出す。

- **判定はコード。AI は Apple の修正内容を日本語に要約するだけ**
- 情報源は **Apple Security Releases 1 本**（`support.apple.com/en-us/100100`）
- 緊急の根拠は **Apple の実悪用記載**と **CISA KEV**。どちらも公式から直接取る
- NW とはトリガー・シート・台帳が別。片方が落ちてももう片方は止まらない
- **1 リリース 1 通知。**赤も緑もそのリリースの判定として届く

## 4. 利用者の作法（守ること）

- **次の作業は必ず聞いてから動く。**勝手に機能追加しない
- **結論ファーストで答える。**手順の羅列や過度な言い換えは不要
- **「なぜその値・その設計か」を必ず問われる。**根拠のない断定は指摘される。
  適当に置いた値は「根拠はない」と正直に言う
- **「パッチワークになっていないか」「本質からずれていないか」を繰り返し問われる**
- **知らないことは調べる。推測で答えない**
- **行数や工数を、依存関係を確認せずに言わない**
- **忖度のない FB を求められる。**違うと思ったら根拠を出して反論してよい。
  ただし**利用者の指摘のほうが正しかったことが何度もある。**データで確かめてから答える
- **自分の出した指示も疑われる。**「それに意味あるの？」と聞かれたら、
  やらない側に倒れる理由がないか数字で確かめ直すこと（2026-09-11 に 1 件撤回した）
- コミット・push は依頼があるまでしない
- チームは git を見られない。**運用に必要なことは GAS の `readme.gs` に書く**

## 5. 踏んだ罠（同じ手を二度やらないため）

**すべて「実行は成功したように見えるのに結果が壊れる」型。ローカルのテストでは出ない。**

| 罠 | 教訓 |
|---|---|
| GDMF が SSL Error | Apple 独自ルート CA。`validateHttpsCertificates:false` も効かない。**再挑戦しない** |
| Developer RSS は 11 か月で 53 件しかない | 旧メジャーの更新を載せない。情報源から外した |
| 台帳が空のまま実行だけ成功 | 書く前にシートの行数を確認していなかった |
| 81 版なのに 163 行 | 書いた行より下の古い行を消していなかった |
| 実悪用を調べていないのに「なし」と表示 | **やっていないことを、やった結果の形で記録していた** |
| 初期取込に PENDING と表示 | 同上。「未評価＝調べていない」「未確認＝調べたが分からない」を分ける |
| 初期取込を Phase 2 ごと素通り | **通知を抑えることと、調べないことは別** |
| 緊急と判定した行を握り潰す | 状態を増やして通知を制御すると事故る。1 リリース 1 通知に畳んだ |
| 実行履歴に「通知は送っていません」と出しながら通知 4 件 | 仕様を変えた後、**記述の側に古い前提が残っていた**（2026-09-11） |
| 管理対象外の行が「詳細が未取得」 | 仮置きの値が、調べに行かない行に残り続けた（2026-09-11。§7-1） |
| macOS 12 で実行履歴が毎日「要確認」 | 台帳に二度と載らない系統について人に判断を求めていた（2026-09-11。§7-2） |

**共通する根は「やっていないことを、やった結果として記録する」。**
台帳の値を見たら「これは調べた結果か？」を常に疑うこと。

**2026-09-11 に増えた教訓**: コードを直しただけでは**すでに書かれた値は直らない**。
「1 回回せば直る」と言う前に、既存行を上書きする条件を読むこと。

## 6. 検証のやり方

scratchpad に node のハーネスを置き、GAS の API をスタブして本体をそのまま読み込む
（セッションが変われば作り直す）。`Utilities` / `Logger` と、v7 側の
`sharedAiCountToday_` / `SLACK_WEBHOOK_PROP` をスタブすれば `macosSelfTest()` が動く
（`postSlack_` / `kevCatalogWithStatus_` / `callGemini_` の 3 件は落ちる。ローカルに v7 が無いため）。

- 実データは Apple 公式ページと CISA KEV を curl で取って使う。**作り話のデータで判定を確かめない**
- **判定ロジックに触るときは、変更前の挙動を全パターン記録してから作業する。**
- **回帰テストは、旧コードに戻して落ちることまで確認する。**通ることだけ見ても意味がない
- **node で 2 ファイルを連結しても GAS のファイル分離は再現できない。**
  分離が絡む変更は実機の `macosSelfTest()` で確かめる

## 6.5 削った要件（2026-09-11）

**利用者が求めていない機能が積み上がっていた。**指摘を受けて落とした。

| 削ったもの | 出どころ | なぜ不要だったか |
|---|---|---|
| `追跡状態` 列と「配り終わったら適用済と書く」運用 | v3.2 の原則 3。**利用者との合意事項に無い** | 通知量に効かない。判定が変わらなければ再通知しないので、書かなくても何も起きない（実測: 06:54 は緊急 1 / 通知 0）。止めるのは日々の再取得だけで、行は 90 日で消える |
| `前回の配布判断` 列 | — | 読む場所が Slack の「前回は…」1 行だけだった。その実行のあいだメモリで持てば足りる |
| `macosChildText_` / `MACOS_E_UNKNOWN` | RSS を外したときの残骸 | 参照ゼロ |
| Slack の注意書き 2 つ（「急ぎの対応は不要は安全の保証ではない」「端末モデル / CPU 個別の条件は対象外」） | — | 毎通に出る文は数回で背景になる。リード文が既に「実悪用記載なし・KEV 一致なし」と守備範囲を書いている。読み方は readme.gs で 1 回覚える（ccb32bc） |

**残した列**: `実悪用の記載`。Apple 由来の 🔴 の根拠がここにしか無く、
「標的型か、広く悪用されているか」で人が動く速さを変える材料になる（実測で直近 40 リリース中 6 件が該当）。

**要件でないものを足していないか、定期的に疑うこと。**
「シンプルに通知してほしいだけ」が利用者の要件。

## 7. 未解決・申し送り

### 1. 管理対象外 4 行の Security状態が「詳細が未取得」のまま

`15.7.9 / 14.8.9 / 15.7.8 / 14.8.8`。修正（b1bf3a5）は**これから入る行**にしか効かない。
`macosUpsertReleases_` の既存行の分岐は、空か「Apple索引に未掲載」のときしか上書きしないため。

**手当てしない判断。**判定にも通知にも一切効かず、公開日から 90 日で台帳から外れる
（15.7.8 / 14.8.8 は 2026-10-25、15.7.9 / 14.8.9 は 2026-11-04）。

手で書き換えないこと。**台帳はツールが書く場所で、人が書く列は 1 つも無い。**
手で入れた値はツールの値と見分けが付かなくなる。いまの「仮置きの消し忘れ」より悪い。

### 2. `macosEnsureManagedRows_` が情報源の全メジャーを人に聞く

窓のフィルタが無く、Apple 索引の全 81 版から系統を拾う。実測:

| 系統 | 最新版の公開 | 直近 90 日 |
|---|---|---|
| macOS 26 | 25 日前 | 4 版 |
| macOS 15 / 14 | 36 日前 | 各 2 版 |
| macOS 13 | **387 日前** | 0 版 |
| macOS 12 | **774 日前** | 0 版 |

台帳に入るのは直近 90 日ぶんだけなので、**12 も 13 も二度と載らない。**
それでも `macosCheckReadiness_` が未設定を毎回検出し、`macosWriteRunLog_` は
備考が 1 つでもあれば結果を「要確認」にする。
→ **答えるまで毎日「要確認」が点灯し、本当の異常が埋もれる。**

2026-09-11 は 12 に FALSE を入れて消した。**構造は直していない。**
台帳に載りうる系統だけ聞くのが筋だが、挙動の変更なので未着手。

### 3. AI 要約が付かない日がある

稼働初日は 4 通とも要約なし（06:33 は Gemini 503、06:52 は枠上限）。
枠は NW と合算で 1 日 12 回（`MACOS_AI_DAILY_BUDGET`）。当日の合計は
スクリプト プロパティ `AI_COUNT_yyyyMMdd` で見られる。

初日は台帳を 2 回作り直した影響が大きい。**平常運転でどうなるかは、
実行履歴の「AI呼び出し」列を数日見てから判断する。**
配布判断は AI に依存しないので通知そのものは止まらない。
