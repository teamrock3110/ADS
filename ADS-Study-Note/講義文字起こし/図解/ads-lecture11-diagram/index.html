AI-Driven Rulesには「理解できないものは作るな」があります。毎日AIを使ってきたのに、中身はよくわかっていない ── このまま卒業はできません。仕組みを知るべき理由は3つあります。

仕組みを知るべき3つの理由

復習 ── LLMとは？

大規模言語モデル（Large Language Model）のこと。ChatGPT・Claude・Geminiなどの中身にあたる、生成AIの本体です。膨大な文章を学習して「次に来る言葉」を予測することで、文章を生成しています。

出題 ── マルかバツか、まずは4問まとめて

第1問 AIはあなたのパソコンの中で動いている
第2問 長い会話では、やり取りを毎回丸ごとAIに送り直している
第3問 チャットにつけたファイルはAIが自分で開いて読んでいる
第4問 難しいお願いのときほど、通信の回数は増えている

直感でOK、調べるのはなしです。4問すべてに自分の答えを決めてから、この先の答え合わせに進んでください。

第1問

AIはあなたのパソコンの中で動いている

答え バツ

パソコンの中にAIはいません。Cursorをダウンロードしても、その中にAIが入っているわけではない。チャットを送信した瞬間、文章がインターネットを渡って遠くのデータセンターに届き、そこでAIが動いています。返事が一瞬で来るので中にいるように錯覚しますが、毎回この往復をしています。

Anthropicなどの

パソコン内で動くオープンソースのLLMも存在しますが、毎日使っている最新AIの能力にははるかに及びません。最新に近いモデルを動かすには、どんなに安くても込み込みで1000万円近くかかるのが現状です。

LLMの大原則 ── 今回の話は全部ここから始まる

テキストを送ったら、テキストを返す。それだけ。

どれだけ賢くなっても、できることは「文章を読む・文章を書く」だけです

第2問

長い会話では、やり取りを毎回丸ごとAIに送り直している

答え マル

LLMには記憶がありません。さっき自分が返した内容すら覚えていない。何回挨拶しても「はじめまして」です。会話が続いているように感じるのは、通信のたびにこれまでのやり取りを全部つけて送り直しているからです。

会話が長くなるほど、毎回送る荷物が膨らんでいく

依頼 1
2通目
依頼 1 ＋ 返答 1
依頼 2
3通目
依頼 1 ＋ 返答 1
依頼 2 ＋ 返答 2
依頼 3
「覚えてくれている」のではなく、実行係（Cursorなど）が過去のやり取りごと送り直してくれている。途中でモデルをClaudeからGeminiに切り替えても会話が続くのは、このためです。
第3問

チャットにつけたファイルはAIが自分で開いて読んでいる

LLMはあなたのパソコンのファイルを開けません。テキストを返すことしかできないのに、なぜCursorに「この原稿を直して」と頼むと、ちゃんとファイルを読んで修正してくれるのか。ここが今日の核心です。

答え バツ

ファイルを開くのはいつも実行係（Cursor）です。LLMはあなたのパソコンのファイルに一切触れないので、そのままでは読むことも直すこともできません。それでもちゃんと修正されるのはなぜか。「この原稿を直して」と送ってから直るまでの裏側を、順を追って見ていきます。実は実行係とLLMの間で2往復の通信が起きています。

往復 1 まずLLMに「どうすればいい？」と相談する
1
あなた → 実行係: チャットに「この原稿を直して」と入力して送信する
2
実行係 → LLM: あなたの指示・これまでのやり取り・道具のカタログを1通のテキストにまとめて送る。開いているファイルの「名前」は伝えるが、中身はまだ送らない
3
LLM → 実行係: カタログを見て「Read file という道具でそのファイルを読んで」と文章で返す。LLMは自分でファイルを開けないので、開ける道具を持つ実行係にお願いすることしかできない
実行係が言われた通りに Read file を実行し、ファイルの中身を手に入れる
往復 2 中身を渡して、修正してもらう
4
実行係 → LLM: 読み込んだファイルの中身を送る。LLMはここで初めて原稿の中身を知る
5
LLM → 実行係: 中身を読んで修正後の文章を考え、「Edit file という道具でこう書き換えて」と返す
6
実行係: 言われた通りにファイルを書き換えて保存。ここで初めて原稿が直る

なぜ最初からファイルの中身を送らないの？

仕組みとしては最初から送ることもできます。それでもこの形なのは、どの道具をどう使うかをLLM自身に考えさせたいから。今は「そういうものなんだ」と理解できていればOKです。

ファンクションコーリング

今見てきた「実行係が道具のカタログを送り、LLMがカタログから道具を選んで指示し、実行係が遂行する」という一連の流れには名前がついています。それがファンクションコーリング（Function Calling）。ファンクション＝機能、コーリング＝呼び出し。実行係の持つ機能をLLMが呼び出す、そのままの名前です。

CursorもClaude Codeも、ChatGPTがネットを検索するときも、AIが道具を使う場面は全部この仕組みで動いています。道具のカタログが毎回送られるのは、LLMが何も記憶しないから。あなたがAIを組み込んだツールを作るときも、必ずこの仕組みを使うことになります。
第4問

難しいお願いのときほど、通信の回数は増えている

答え マル

複雑な仕事ではたくさんの道具を使います。それも一発ではありません。相談 → 道具の指示 → 実行 → 結果を報告 → また指示…… を何度も繰り返して、複雑な仕事を遂行していきます。

相談する
カタログ＋依頼を送る
LLMが指示
「この道具を使って」
実行係が遂行
結果をまたLLMへ
仕事が終わるまで、この流れを何度も繰り返す

仕分けワーク ── どこまでがLLMの仕事なのか

ワークでは「この原稿を直して」の裏側で起きる6つの動作A〜Fのうち、LLM本体が自分でやっているものはどれかを仕分けました。答えはこうです。

A ファイルを開く 実行係
B 送られてきたファイルの中身を読む LLM
C どう直すかを考えて、修正後の文章を生成する LLM
D ファイルに書き込んで保存する 実行係
E コマンドを実行する 実行係
F これまでのやり取りを思い出す 正確には誰にも「思い出せない」。実行係が保存していたやり取りを、毎回まるごと送り直している 実行係
LLMがやるのは「読んで、考えて、書く」だけで、手を動かす仕事は全部実行係。ただしLLMは、ファイルを開く「道具を使いたい」と文章で頼むことはできます。

必ず覚えて帰りたい公式

AIエージェント ＝ LLM × ツール

考えるのはLLM。実際にファイルを開いたり書き換えたりするのは、実行係が持つツールです。どちらか片方だけでは働くAIにはならず、2つが掛け合わさって初めてAIエージェントになります。この線引きができると、LLMには考えることに集中させ、足りない部分を道具と情報で支える設計ができる ── AI-Driven Rules「90点から100点の戦いに備えよ」に繋がる理解です。

実際のツールの中で動くファンクションコーリング

Surprise社で毎日動いている、AIを組み込んだ2つのツールが紹介されました。LLMと実行係の分業が、実際のツールの中でどう動いているかの実例です。

Quiz Studio
本気AIドリルの問題を作るツール

1シリーズ600〜700問の教材を、ツール内のAIエージェントが下書きし、別のAIがレビューし、機械のチェックが検品する仕組み。仕上げは人間が全問目視します。Claude Codeをアプリに組み込めるAnthropicのライブラリ「エージェントSDK」で実装されています。

Article Assistant
AI時代の動画編集ツール（開発中・仮名）

動画編集をすべてチャットからできるツール。誤字脱字チェックやAI生成画像での背景差し替えを、専門家ごとに分けたエージェントが実行します。「原稿を読む道具」「修正を書き込む道具」の正体はプログラムの関数です。

なぜエージェントの役割を分けるのか

1つのエージェントに複雑な仕事を丸ごと任せると、9割まではできても最後の1割の精度が出ないからです。仕事を誤字脱字チェック・画像生成のような小さな単位に分割し、担当のエージェントごとに精度を100点までチューニングしていく。AI-Driven Rules「90点から100点の戦いに備えよ」の実践です。

AIに送られている「1通のテキスト」の中身

チャットを送信すると、最終的にLLMに届くのは1通の長いテキストです。あなたが入力した文章は、その一番最後の一部にすぎません。中身を開けてみると、こうなっています。

LLMに届く1通のテキスト
システムプロンプト ── 見えない前置き

「丁寧に答える」「危ないことは断る」など返事の型を決める、ユーザーには変更できない文章。ツールごとに違うため、同じ指示でもCursorとClaude Codeで返信が変わる。

あなたのルール ── CLAUDE.md / Cursor Rules

AIに「ルール機能」があるわけではなく、実行係がルールに書いた内容を毎回貼って送っている。ルール設定とは、毎回AIに送る指示を決めること。

呼び出したスキル ── カタログは毎回、本文は必要なときだけ

SKILL.mdのディスクリプションだけを集めた「スキルカタログ」。AIが「これを使う」と判断したら、実行係が本文を送る。

道具の一覧 ── ツールのカタログ

ファイルを読む・書く・コマンドを実行するなど、実行係が持っている道具の全カタログ。使う・使わないにかかわらず毎回送られる。

これまでのやり取り

これまでの会話の履歴が毎回丸ごと送られる。会話が長くなるほどここが膨らむ。

今回の頼み

あなたがチャットに入力した文章。送られるテキスト全体から見れば、ほんの一部にすぎない。

ワークで考えた「スキルはなぜ名前を覚えていなくても動くのか」

「美容室を予約して」と書くだけでスキルが動くのは、「何ができて、どんなときに使うか」を書いたディスクリプションが毎回AIに送られているからです。AIが「使う」と判断して初めて、実行係が本文を送る。ファンクションコーリングと同じ考え方です。

画像を貼ったときはどうなる？

文章も画像も、そのままLLMが読んでいるわけではありません。文章は言葉を細かく刻み、画像は小さなタイルに分割して、どちらも「トークン」と呼ばれる数値の列に変換されてから処理されます。

枠の取り合い ── コンテキストウィンドウ

LLMが受け取れるトークンには上限があります。第2回で学んだ「AIの3つの壁」の1つ、コンテキストウィンドウです。ここで大事なのは、送られる1通のテキストの中身すべてが同じ1つの枠を取り合っているということです。

会話が長くなると枠が埋まり、頭脳は大事なところを見失っていく。新しいチャットで賢さが戻るのは、枠を取り戻しているから

よくある誤解

会話が長くなるとAIの調子が落ちるのは、AIが疲れてくるからではありません。LLMは記憶を持たないので、毎回まっさらな状態です。変わっているのは送るテキストのほう。やり取りを重ねるほどテキストが長くなって枠を圧迫し、大事な情報が埋もれていきます。

そのトークンは、枠を消費するに値するか

Anthropicの技術ブログで語られた考え方。LLMを使うとはコンテキストウィンドウを取り合うこと。だからスキルは短く書く。いらない資料を渡さない。枠は有限だからです。

3つのエンジニアリングの関係

漠然とした概念ではなく、範囲の違いとして整理できる

ハーネスエンジニアリング

AIエージェント（LLM×ツール）が繰り返し動く中で、間違った方向に行かないように環境全体を整える

コンテキストエンジニアリング

送られる1通のテキスト全体が、AIにとって適切な状態になるように整える

プロンプトエンジニアリング

テキストの一番最後、ユーザーの指示だけをチューニングする

MCPも正体はファンクションコーリングです。連携先の「道具カタログ」を毎回LLMに渡しているだけ。LLMの本質を理解すれば、すべての知識が繋がっていきます。

Surprise Ritual Timer

毎朝の朝会は「振り返り → マインドセット読み込み → アクションプラン策定」の3ステップ。1人60秒の発表のたびにスマホでタイマーを測り直す面倒を、Slackからワンポチの自動進行で解消し、今では毎朝全員が使っています。

朝活したいけど意志の力に頼ると続かない。そこで「仲間に晒される仕組み」で続けさせる。朝の写真で証明すると連続記録が伸び、サボるとフレンドのフィードに晒されます。コンセプトは「BeReal × Duolingo」です。

キャラ画像生成ツール

図解へのコメントは「箇所を選ぶ → 入力 → 投稿」の繰り返しが面倒。図解を見ながら話すだけで、AIがどの箇所へのフィードバックかを特定してピンを自動配置してくれます。操作は音声入力の開始と終了の2クリックだけです。

まとめ ── 第11回講義で覚えておきたいこと

01

AIエージェント＝LLM×ツール

LLMはテキストを受け取って返すだけ。記憶もなく、ファイルにも触れない。道具のカタログを渡され、実行係が手足になることで初めて働くAIになる。画面に流れる「Read file」は、その分業が動いている証拠。

02

AIは毎回送られる1通のテキストの中身しか知らない

あなたの指示だけでなく、システムプロンプト・ルール・スキル・道具の一覧・会話の履歴が、毎回1通のテキストにまとめて送られている。その全部が限られた1つの枠を取り合うから、「そのトークンは枠を消費するに値するか」を考えて中身を整える。

03

卒業制作は「毎日のちょっとした面倒」から

多くの人に使われるサービスではなく、自分もしくは誰か1人がずっと使い続けるツールを目指す。非エンジニアでも1泊2日で動くものが作れた。小さな面倒に気づくことが勝利の第一歩。

カレンダーの時間を押さえる、同じ時間にカフェに行くなど、やらざるを得ない環境を作って自分のツールを作り上げてください。ラストスパートです。
