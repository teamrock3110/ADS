Markdown

人間が見やすく読むための自由な記述形式。AIものびのび書ける反面、書き方が揺れやすく、プログラムには扱いにくい。

JSON

AIの育て方 ── 小さく始めて育てる

繰り返す仕事をAIに任せたいとき、いきなり完璧を目指してはいけません。これはスキルの育て方そのもの。スキルとは「AIをベテランにする自分専用の手順書」です。

AI-Driven Rules ⑦

スキルを育て続けろ

AIを育てる5つのステップ

1

ゴールを言葉にする

ゴールが曖昧だと、AIの出したものを評価できないし、AIもどこへ向かえばいいかわからない。「読んだ人がどうなれば成功か」を最初に決める。

2

まず雑に1回投げる（ゼロショット）

見本も指示もなしで、最小限でやらせてみる。これは偵察。雑に頼んで満足できるならそれで十分。細かい指示はかえってAIの性能を下げることもある。

3

手本を1個、自分の手で作る

「これぞ」という模範解答を1つ書く。抽象的な指示より、正解を1つ見せる方が品質がそろう（Rules その8）。最初からたくさん用意しなくていい。

4

足りなければ「軽い打ち手」から改善する

手本を渡しても100点が毎回出るわけではない。でもいきなり大手術をしない。次の「打ち手の階段」を下から登る。

5

磨き続ける

「これはダメ、あれもダメ」と足し算でダメ出しすると、基礎的なことも守れなくなる。何を直したかを自分で認知しながら磨く。

打ち手の階段

下に行くほど軽い打ち手。必ず下から始める。ゴールに届いたら、それ以上やらなくていい

4. 仕組みで守る いちばん重い
バリデーションなどプログラムで機械的にチェックする
3. 別の目でチェック
サブエージェント（別のAI）にレビューしてもらう
2. 頼み方を整える
AIへの指示の言葉を少しだけ足す（プロンプト改善）
1. 手本を足す いちばん軽い・まずここから
模範解答をもう1個渡す（2〜3個あればAIは十分理解する）

サブエージェントのレビューには「限界」がある

サブエージェントとは、ここまでのやり取りを知らない別のAIに仕事を頼むこと。客観的なフィードバックがもらえる一方、根本的なやり直しは提案してくれません。

お弁当のレビューで考えると
「野菜を増やしては」「鮭の焼き方を工夫しては」 ← 改善案は出る
「そもそもサンドイッチでは？」 ← 根本的な提案は出ない

「レビューで問題なし＝完璧」ではない。レビューは“今あるものをどう良くするか”の視点になりやすい、と理解しておく。

サーバーって何をしてるの？

Markdown のクイズを「ブラウザで見やすく表示する」道具がビューアー（Quiz Viewer）です。Markdown のままでは見づらいので、ブラウザで表示できるようにする ── これは立派なWebアプリケーション開発です。動かすには「サーバー」を起動する必要があります。

ターミナル
$ cd /Users/you/src/quiz-studio
$ pnpm dev
▲ Next.js ── ready
ローカル: http://localhost:3000
ターミナルでは「今どこの場所で実行するか」が重要。cd（チェンジディレクトリ＝場所を移動するコマンド）でアプリのある場所へ。よくわからなければ「実行コマンドをフルパスで出して」とAIに頼めばOK。localhost は「自分のパソコンの中だけに通じる住所」です。
ワーク

「pnpm dev というサーバーは、何をやってくれているのか？」を自分なりの言葉で考えてみる。AIに聞くときは「入社したての社会人でもわかるように説明して」と添えるのがコツ。

pnpm dev は何をしている？

ひとことで言うと「HTML・CSS・JavaScript に変換してくれている」

Next.js のコード
短く楽に書ける「フレームワーク」。HTML/CSS/JSそのものではない
pnpm dev 変換
HTML・CSS・JS
ブラウザが表示できる形
ブラウザで表示
コードを書き換えると即反映される

pnpm は「道具屋さん」

Webアプリ開発では、世界中のエンジニアが作ってくれた便利な道具を借りて使います。その道具がどこにあるかを全部知っていて、集めて管理してくれるのが pnpm。暗記する必要はありません。

小難しい言葉を暗記するのではなく、「要するにこういうもの」と自分が腑に落ちる言葉に直せる人が、学び上手な人。これはプログラミングに限らない。

Markdown → JSON ── データに「型」を持たせる

問題数が少ないうちは Markdown で十分。でも増えてくると限界が見えてきます。きっかけは、AIが起こすちょっとした表記のブレです。

正しい書き方
選択肢：AIへの指示文
AIがたまにやるブレ
Option：AIへの指示文
人間なら「書き方を変えただけだな」と分かる。でもMarkdownを表示するプログラムにとっては大問題でエラーになる。プログラムは微妙なニュアンスを汲み取れない。

対策：バリデーション（機械的なチェック）

バリデーションとは、フォームでメールアドレスの形式が間違っていたら指摘してくれる、あの仕組みと同じ。クイズを作ったあとにプログラムで自動チェックさせます。

バリデーション実行
$ validate lesson-01.md
✗ エラー: 「Option：」は不正な表記です
→ 「選択肢：」を使ってください（3行目）
このチェックを「クイズ作成後に必ず実行する」とスキルに書いておけば、間違った形式が作られてもAIが自分で気づいて直せる。これが打ち手の階段の「仕組みで守る」です。

Markdown と JSON の違い

JSON は「ラベルと中身をいつもセットで書く」構造化されたデータ。フォルダで整理するのと同じ考え方

Markdown
  • 自由に書ける・人間が読みやすい
  • AIがのびのび書ける
  • 箱の中身が厳密に決まらず、プログラムが扱いにくい
JSON
  • 構造化されていてプログラムが扱いやすい
  • データをきっちり定義できる
  • 人間に読みにくく、カッコが1つ抜けるだけで壊れる

JSONを「AIに直接作らせる」かは設計判断

AIに緻密なJSONを作らせると、カッコを閉じることに気を取られて肝心の中身の品質が下がることがある（アテンションの壁）。難しい仕事ほど、形式づくりに頭を使わせない方がいい。

ひとつの解：AIにはMarkdownでのびのび作らせ、プログラムでJSONに変換する。ただし1問だけなら差は出にくい。メリット・デメリットを天秤にかけて自分で決める。

JSON → データベース ── Gitの外の世界へ

JSON をリポジトリで管理している間は、まだ Git の世界にいます。Git はとても頼れる相棒です。でも、データが増えていくと、その相棒が「邪魔」に感じる瞬間が来ます。

差分が見える
何がどう変わったか、自分の目で確認できる
戻せる
コミットしておけば、間違えても前の状態に戻せる
上書き事故を防ぐ
複数人で同じ所を直すとコンフリクトで教えてくれる

Git は「断崖絶壁を登るときの命綱」

少し登っては杭を打ち、命綱をつける。だから安全。でも…

登り始めのうち

こまめに杭を打って命綱をつけるから安全。差分を確認しながら一歩ずつ進める。命綱が機能している状態。

登るのが速くなると

50cmごとに杭を打つのが面倒に。差分が大量に出て認知が追いつかず「もうGitなんて見てない」状態に。命綱が逆にペースを落とす。

「全部Gitで管理するのは限界だ」と感じたとき ── それがデータの保存先をデータベースに移すタイミング。SNSの全投稿をGitに入れないのと同じで、膨大なデータはGitに向かない。

データベースに移ると「AIとの距離」が離れる

AIから見たデータの「取り出しやすさ」が変わる

AIの限界を超えるための3つの道具

スキル

AIをベテランにする自分専用の手順書。繰り返す仕事を固定する。

サブエージェント

別のAIに客観的なレビューを頼む。ただし根本的なやり直しは出てこない。

フック 最初は不要

AIのサボりを強制的になくす仕組み。一番ややこしく設計も難しい。「こういうものがある」と知っておくだけでOK。

01

小さく始めて育てる

ゴールを言葉にし、雑に1回投げ、模範解答を1個作り、軽い打ち手から改善する。スキルもツールも、必要最小限で小さく試すのが王道（スピードを出すな、対話しろ）。

02

保存先が進むほど、AIとの距離が離れる

Markdown → JSON → データベース。できることは増えるが、考えることも増え、AIから遠ざかる。データの管理とAIの性能は密接につながっている。

03

自分の言葉に落とし込む

細かい技術は移り変わるが、本質は変わらない。中学生でもわかる言葉で「要するにこういうこと」と言い換えられることが、次につなげる一番のコツ。

技術的に難しいのは、今回まで

ここから先は新しい概念を覚える時間ではなく、ここまでで手に入れた「作る力」を使いこなしていく時間。Webアプリを作ることがゴールではなく、AIで新しい価値を生むことがゴール。作るのは、あくまで手段です。
