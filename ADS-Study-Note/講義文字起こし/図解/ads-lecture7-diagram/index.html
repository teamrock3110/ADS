今回の重要キーワード

この講義で新たに登場する、理解の土台となる6つの用語です。

ハーネスエンジニアリング

AIの力を引き出しつつ暴走させない仕組みを自分で組む技術。馬具（ハーネス）が語源。プロンプト・コンテキストの上に積み重なる最上位概念。

Markdown

人間が見やすく読むための自由な記述形式。AIも得意だが、プログラムには書き方の揺れが扱いにくい。

candidates/佐藤花子.md
# 佐藤花子
ポジション：エンジニア
評価：4
ステータス：最終面接

JSON

カッコとキーで情報を厳密に構造化する形式。プログラムの処理はシンプルになるが、人間は読みにくく、AIにも精密さが求められる。

candidates.json
{
"name": "佐藤花子",
"position": "エンジニア",
"score": 4,
"status": "最終面接"
}

データベース

複数人で読み書きできる、たくさんの表が入った箱。列ごとに型を決めて間違いを防ぐ。何十万件でも瞬時に検索可能。

candidates テーブル
id name score status
1 佐藤花子 4 最終面接
2 田中太郎 3 一次面接

環境変数

プログラムに直接書けない重要情報（パスワード・APIキー等）の置き場所。流出防止のため .env ファイルや Vercel の設定画面で管理する。

SQL

データベースを操作する言語。ほぼ英語の文。1文字でも間違えば動かないが、今はAIが書いてくれる。

評価4以上の候補者を取り出す例
SELECT * FROM candidates WHERE score >= 4;

ハーネスエンジニアリングとは

ハーネスとは馬に取り付ける装置のこと。拘束具ではなく、馬の力を最大限引き出しつつ、暴走させず意図した方向に走らせるための道具です。これをAIに当てはめたのがハーネスエンジニアリングです。

AIの「馬」としての特性

力を引き出すことと暴走を止めることを同時にやる

抑え込みすぎると

細かく確認を挟みすぎて「もう自分でやった方がはやい」状態に。AIの力が出ない。

放っておくと

AIが自分の判断でどんどん走り出し、とんでもない方向に暴走する。

ハーネスエンジニアリングの役割

力を引き出しつつ、道を外さないように整える仕組みを自分で組む

ハーネスを握っているのは人間。あくまで主体者は人間

ハーネスの5つの軸

ハーネスエンジニアリングを構成する5つの軸です。試行錯誤するときの考え方のフレームワークとして整理できます。

1. データを整理整頓する

Gitリポジトリで情報を構造化して管理する

2. データの探し方を決める

Cursorが裏側でやっていること。AIがどのファイルを見に行くかの設計

3. 作業中の記憶を設計する

コンテキストウィンドウを消費する価値があるかを考える。情報は多ければいいわけではない

4. やり方とルールを明文化する

CLAUDE.md・AGENTS.md・Cursor Rules・スキルの定義

5. 外側からやり直しを強制する

サブエージェントにレビューさせ、NGならやり直させる。「外側から」がポイント

実例：Quiz Studio のハーネス

本気AIドリルのクイズを作成する社内ツール「Quiz Studio」。ハーネスエンジニアリングの実物として、どのようにAIが制御されているかを見てみましょう。

レッスン（クイズ）作成の流れ

AIに「まかせきり」にしない。段階ごとに自動で次の指示が走る

1
下書きを作成
8〜12問のクイズのドラフトを生成
2
サブエージェントがレビュー
1問ごとに別のAIが立ち上がり、品質チェックシートに基づき評価
NG
やり直し
3
修正 → 再レビュー
合格するまで何度でもやり直しが走る
OK
4
ユーザー目線フィードバック
批判的なユーザー視点で問題を解き、改善を提案
機械的チェック
  • 使用禁止ワードが含まれていないか
  • 問題数が規定範囲（8〜12問）か
  • 問題文の長さが適切か
AIレビュー
  • 品質チェックシートに基づく評価
  • 各項目のOK/NGと理由をアウトプット
  • サブエージェントで「やったふり」を防止

フック（自動起動）がカギ

スキルに「この手順でやってね」と書いてもAIは平気でサボる。だから段階ごとにAIが自動で起動する仕組み（フック）を入れて、スキップできない構造にしている。

データ保存の3形式

Webアプリケーションの文字データの保存には3つの選択肢があります。覚悟を決めた一歩を踏み出すごとに、できることが増える代わりに複雑さも増します。

Markdown
人間向け
自由に書ける。Cursorで見やすい
覚悟1
JSON
プログラム向け
構造が厳密。処理がシンプルに
覚悟2
Database
大規模・複数人向け
高速検索。複数人で共有可能
進むほど強力になるが、考えることも増える。自分に必要な段階を選ぶことが大事。

Markdown

UIを作らなくてもツールとして成り立つ

Gitリポジトリに Markdown で情報を置くだけで、Cursor 上の AI が読み書きしてくれる。スキルを置けば同じ品質で繰り返し仕事をさせることも可能。これだけで十分なら先に進む必要はない。

強み
人間が見やすい / AIが得意 / UIが不要
限界
データが増えると見づらい / プログラムが扱いにくい

JSON

プログラムがシンプルになる代わりに、人間は読みにくくなる

カッコとキーで厳密に構造化されたデータ形式。プログラムが「評価のカラムから数字を取る」といった処理を簡潔に書ける。もうエディタではなくツールで見る覚悟が必要。

強み
プログラムがシンプルに / データの揺れが起きにくい
限界
人間が読みにくい / AIにとっても重い作業

Database（データベース）

複数人で読み書きするたくさんの表が入った箱

何十万件のデータから瞬時に検索できる。テーブル（表）ごとにカラムの型（数字・文字など）を厳密に決める。複数人でWebアプリを使いたいなら、ここに来るしかない。

強み
高速検索 / 複数人で共有可能 / データ整合性が高い
限界
AIからの距離が遠い / セットアップが複雑

Markdownは「自由すぎる」問題

Markdownは人間に読みやすいが、プログラムには扱いにくい。なぜなら書き方が統一されないからです。

3人分のデータ、同じ意味なのに書き方がバラバラ

人間は理解できるが、プログラムはエラーを出す

佐藤さん
評価：4
OK
田中さん
評価：A
数字を期待 → エラー
鈴木さん
レビュー：5
「評価」を期待 → エラー
プログラムは人間のように「意味を推測」できない。1文字の違いでもエラーになる。これがMarkdownでの開発が破綻する根本原因。

AIとデータの距離を考える

データの保存形式を選ぶとき、AIとの距離という観点が重要です。データベースは強力だが、AIにとっては遠い場所にある情報です。

AIから見た「データの近さ」

近い
Markdown（リポジトリ内）
手元の紙。すぐ読める。すぐ書ける
近い
JSON（リポジトリ内）
手元だが精密に書く必要あり。AIの注意力を消費
遠い
Database（サーバー上）
棚の奥。SQL を発行して取ってこないと見えない。失敗することも

これがハーネスエンジニアリングの入り口

どのデータをどこに保存するか考えること自体が、すでにハーネスエンジニアリングの実践。AIにとって見やすい場所に必要な情報を整理し、データベースは大量データの管理に特化させる ── この使い分けがAIの性能の限界を引き出す鍵。

画像・動画・音声の保存

文字以外のデータ（バイナリーデータ）は、文字データとは別の場所に保存するのが一般的です。

文字データ
Gitリポジトリ / JSON / Database
Markdown JSON プログラム SQL
バイナリーデータ（文字以外）
ストレージ専用サービス（Blob等）
画像 動画 音声 PDF

Gitリポジトリに画像を大量に入れてはいけない理由

Gitは文字の差分管理が得意だが、画像は1ピクセル変えても丸ごと別ファイル扱い
リポジトリの容量目安は約1GB。画像を大量に入れるとすぐ限界に
