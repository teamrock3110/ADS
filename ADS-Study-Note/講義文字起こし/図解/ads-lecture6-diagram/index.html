STEP 1 ── PoC：最初に試し打ちする

PoC（Proof of Concept＝概念実証）は、やりたいことが本当にできるのかを、小さく試し打ちする工程。「動かなかったら全部終わり」な技術が含まれているなら、最初にここを潰しておくのが鉄則です。

PoCをサボると起きる落とし穴

最後の最後で「思いもよらず動かない」
想定と動きが違って手戻り
実はお金がかかる仕様だった
思ったより使いにくかった
terminal — PoC 用の使い捨てフォルダ
$ mkdir ~/src/zukai-temp
↳ 半角英数で。日本語はエラー要因になりがち
$ cursor ~/src/zukai-temp
↳ AIに「Surgeでサンプル動かして」と依頼
✓ Surgeで Web ページが公開できる → 検証OK
PoCのコツ: 使い捨て前提なので名前は雑でOK（zukai-temp など）。検証が終わったらフォルダごと消す。

GitHubはコード版のGoogle Driveです（ざっくり理解）。コード・設定ファイル・ドキュメントを置いておく場所。リポジトリ = 1プロジェクト分の箱で、原則「1プロジェクト1リポジトリ」。

どこからでも開ける

.gitignore ── Gitに「見えない」ことにするファイル

.gitignore に書いたファイル・フォルダは、Gitが追跡しなくなる。この理解抜きに開発は不可能。

1. APIキー・パスワード
代表は .env。家の鍵・クレカ情報と同じ扱い。プライベートリポジトリでも絶対にコミットしない
2. 自動生成された巨大フォルダ
代表は node_modules。便利道具が大量に詰まっている。コマンドで再生成できる
3. OSが勝手に置くゴミ
Macの .DS_Store / Windowsの Thumbs.db
.cursorignore も覚えておく: Cursor上でAIに「無視させる」ファイルを指定できる。APIキーをAIが勝手に読んで公開しちゃう、なんて事故を防げる。

STEP 3 ── Clone：ファイルじゃなく「作業場」が来る

git clone は、ただファイルをコピーするのとは違う。完全な作業場が1つ立ち上がるのがクローンの正体です。

Cloneで一緒に来る4つのもの

1. 完全なファイル
今の最新の全データ
2. 過去の全履歴
誰がいつ何をしたか
3. 送り先の住所
どの倉庫から来たか
4. 作業位置の情報
どのブランチ/履歴にいるか

GitとGoogle Driveの違い ── 思想がまったく違う

Google Drive / Dropbox

同期前提。ファイルは常に1つ。誰かが触った瞬間、全員に反映される。

誰かが消したら全員の手元から消える
Git

非同期前提。それぞれの作業場で自由に進めて、区切りで送り合う。

同じ場所を編集した時はコンフリクトで警告

.git ── Gitの正体は1つの隠しフォルダ

.git（ドットで始まる＝隠しフォルダ）にすべてが入っている。コミットメッセージも、過去の履歴も、送り先の住所もここ。これを消すとGitの履歴が全部消える。

Cursorのソースコントロールパネルが見ているのは、この .git の中身。「なんかいい感じに動く」ではなく、どんな仕組みで動いているかまで理解しておく。

STEP 4 ── AIルール：毎回言うのをやめる

開発を進めるなかで「これ毎回お願いしているな」と気づくことがある。それをあらかじめAIに伝わっている状態にすると効率がいい。Cursor で使えるルールは大きく3種類です。

Cursor Rules

.cursor/rules/

Cursor専用。Cursor以外では読まれない。

AGENTS.md

リポジトリ直下

業界共通規格。Codex・Antigravity などが読む。

CLAUDE.md

リポジトリ直下

Claude Code 一択。Cursor も設定で読める。

おすすめ: どれか1つに決めて集約する

ルールが散らばっていると整理できず崩壊する。本質的に書く内容は変わらないので、自分の主戦場のツールに合わせて決め打ちする。Cursor の設定で「サードパーティのルール読み込み」をONにすれば、CLAUDE.md も読まれる。

AIルールは「夢を詰め込む場所」ではない

ルールを追加すると
  • その1点では賢くなる
同時に起きること
  • コンテキストウィンドウを消費
  • それ以外の部分は賢くなくなる
  • 多すぎると守らなくなる
AI向けルールは万能ではない。夢を詰め込む場所ではなく、静かにそっと優しく支えてくれる土台。極力簡潔・洗練された状態を保つ。

STEP 5–7 ── 詰める → 見せる → 仕組みにする

開発する前に grill-me で何を作るか詰める。次に 模範解答を1枚作る。それから スキル化して再現可能にする。この順番が一番速い。

STEP 5: Grill-me で詰める

AI-Driven Rules #9「スピードを出すな 対話しろ」

1問ずつ容赦なく質問してきて、分岐を全部解決するまで進まないスキル。「こんな感じで作って」という抽象指示を投げる前に、自分が何をしたいのかを言語化する。

ぼやけたスキルが完成するのはAIのせいじゃない。自分が何をしたいかわかっていないから。

STEP 6: 模範解答を1枚作る

AI-Driven Rules #8「抽象指示より模範解答を作れ」

スキルが自動で出してくれる「理想形」を、先に1枚だけ手で（AIと協力して）作る。これがAIへの最も正確な指示になる。図解なら Tailwind CSS を使うように伝えるのがおすすめ。

STEP 7: スキルにして再現可能にする

creating-skills を使うと洗練されたスキルが作れる

AI業界共通の規格。SKILL.md という名前で書く。AIが起動時に読むのは description だけ。本文は呼び出された時に読まれる。

SSoT（Single Source of Truth＝情報の正本は1箇所）違反に注意: 模範解答を見ればわかることをSKILL.md本文に書かない。両方更新が必要になりメンテが破綻する。

スキル・ルールは「ペットを飼う」のと同じ

一度作ったら最後まで責任を持って面倒を見る。放置すると、自分が知らないところで暴走して事故を起こす（講師の実例：半年前のメンバー作のスキルが想定外に動いてコードが全消し）。同じ作業を3回繰り返したらルール/スキル化が目安。

STEP 8 ── Surge：AIとプログラムの境界を引く

スキルが完成したら、Surge にアップする処理まで自動化する。AI-Driven Rules #10「1クリックを減らせ」── 毎回手作業を不要にして生産性を上げます。

どこまでAI / どこからプログラム？

AIに任せる
  • 図解を作る（クリエイティブ）
  • 文章の要約・言い換え
  • 柔軟な判断が必要なもの
プログラムにやらせる
  • HTMLをSurgeにアップ
  • 同じ処理を確実に繰り返す
  • 5回に1回でも失敗が許せない処理
境界線の判断は人間にしかできない。AIには見えないコンテキスト（精度要求・コスト・代替手段）があるから。

Surge と Next.js の使い分け

Next.jsの中身 ── 鉄板フレームワークの構造

Next.js は React + TypeScript + App Router + サーバー機能 をひとまとめにした「鉄板の家を建てるキット」。第5回でも触れたけど、もう一段解像度を上げて見ます。

React ── 画面作りの事実上標準

画面を小さな部品（コンポーネント）に分けて再利用できる。同じパーツを10ヶ所コピペする苦行が消える。Next.jsを使う＝Reactを使う。

TypeScript ── 細いネジを警告してくれる

JavaScriptの上位互換。家を建てるとき太いネジが必要な場所に細いネジを打つと「ダメだよ」と教えてくれる。AIの精度も上がる。

App Router ── フォルダ構造 = URL

URLとページの紐付けが面倒だったのを解決。app/blog/page.tsx なら /blog が自動で開ける。

プロジェクトの中身（抜粋）

my-app/
app/ # ページを置く場所（App Router）
page.tsx # トップページ
blog/
page.tsx # /blog のページ
layout.tsx # 共通の枠組み
components/ # 共通部品（ボタンなど）
ui/ # shadcn/uiから運び込んだ部品
public/ # 画像・動画など無加工で配信
package.json # 使う便利道具のリスト
.next/ # ビルド結果が入る（触らない）
node_modules/ # 道具屋が運んできた中身（.gitignore）

.tsx は「HTMLの役割を果たすTypeScript」

Next.jsの開発では HTMLファイルを直接編集しない。.tsx ファイルを書くと、最終的に .next/ の中にHTML/CSS/JSとして自動生成される。ブラウザで動くのは結局HTML/CSS/JSという原則は変わらない。

shadcn/ui と Tailwind ── 見た目の鉄板コンビ

shadcn/ui = プロが作ったオシャレパーツ集。ボタン・カード・ダイアログなど50種類以上。中身は Tailwind CSS で作られている。

ボタン1つを自作する場合に考えること

通常時 ホバー時 押した時 無効時 フォーカス時 Enter押し時

これを全部手作業 = 大変。shadcn/ui なら動きも含めて最初からセット済み。

shadcn/ui と Tailwind の関係

shadcn/ui

ブラウザで動くのはあくまで HTML/CSS/JavaScript。Tailwind・shadcn/ui はビルド時に普通のCSSに変換される。
