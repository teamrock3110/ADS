# ASCIIアートガイド（Markdown出力向け）

図解セクションは必ずASCIIアートで構造を示す。
「読み始める前に全体像が頭に入る」ことが、理解の速度を決める。

Markdownでは **コードブロック（\`\`\`）** 内にASCIIを書く。

---

## 使用する文字セット

```
ボックス: ┌ ─ ┐ │ └ ┘ ├ ┤ ┬ ┴ ┼
矢印:     → ← ↑ ↓ ↔ ──▶ ◀── ▼
ラベル:   [ ] ( ) 半角スペースで整列
区切り:   ═══ ─── ···
状態:     ✓ ✗ ★ ※
```

---

## トピック性質別パターン

### パターンA: アナロジー図（「Xとは何か」）

身近なたとえの登場人物を配置し、矢印で関係を示す。主役を中央に大きく。

```
例: APIの役割（レストランのたとえ）

  [あなた / アプリ]
        │
        │ 「パスタください」（リクエスト）
        ▼
  ┌─────────────────┐
  │   API（ウェイター）│  ← 仲介役。中身を知らなくてよい
  └────────┬────────┘
           │ 依頼
           ▼
  [サーバー / 厨房]  ──▶ 処理 ──▶ 結果（レスポンス）
           │
           └──────────────────▶ [あなた / アプリ] に届く
```

### パターンB: ステップフロー（「Xはどう動くか」）

番号つきで左から右（長い場合は上から下）。

```
例: APIリクエスト〜レスポンスの流れ

  [1] リクエスト送信     [2] APIが受け取る      [3] サーバーが処理     [4] レスポンス返却
  アプリが「情報ください」  内容をチェック・認証    DB検索・計算を実行      結果をアプリに返す
        │                      │                      │                      │
        └──────────────────────┴──────────────────────┴──────────────────────┘
```

### パターンC: 左右対比（「XとYの違い」）

同じ観点を同じ行に揃える。

```
例: APIがある世界 vs ない世界

  【APIがない世界】                    【APIがある世界】
  天気 → 自前で気象観測を構築 ✗      天気 → 天気予報APIに問い合わせ ✓
  決済 → カード処理を自前開発 ✗      決済 → Stripe APIに任せる ✓
  地図 → 地図データを自前作成 ✗      地図 → Google Maps APIで表示 ✓
```

### パターンD: ネットワーク構成図

コンポーネントの配置関係・通信の流れを示す。

```
例: SAML認証フロー

ユーザー          SP（サービス）          IdP（Okta等）
   │                   │                      │
   │  ① アクセス       │                      │
   │──────────────────▶│                      │
   │                   │  ② SAMLリクエスト    │
   │                   │─────────────────────▶│
   │                   │                      │ ③ 認証画面
   │◀─────────────────────────────────────────│
   │  ④ ID/PW入力      │                      │
   │─────────────────────────────────────────▶│
   │                   │  ⑤ SAMLアサーション  │
   │                   │◀─────────────────────│
   │  ⑥ アクセス許可   │                      │
   │◀──────────────────│                      │
```

### パターンE: 正常時 vs 障害時

2つの状態を縦に並べて差分を明確にする。

```
【正常時】
WLC ──▶ Primary(1812) ──▶ Accept/Reject ──▶ 接続OK

【Primaryダウン時】
WLC ──▶ Primary(1812) ──×  （タイムアウト）
    └──▶ Secondary(1812) ──▶ Accept/Reject ──▶ 接続OK
```

### パターンF: 階層・包含関係

「Aの中にBがあり、BはCを使う」構造を示す。

```
例: Okta Orgの構成

┌─── Okta Org ─────────────────────────────────┐
│  ┌── Directory ──────┐  ┌── Applications ──┐  │
│  │  Users / Groups    │  │  Slack / Google  │  │
│  └──────────────────┘  └─────────────────┘  │
│           │                       │           │
│           └──────── SAML/OIDC ────┘           │
└───────────────────────────────────────────────┘
```

### パターンG: 設定値とフローの対応

設定パラメータがどこに影響するかを矢印で示す。

```
  [timeout = 5秒]  ──── 応答待ち時間を制御
  [retries = 3回]  ──── 再送回数を制御

  最大遅延 = timeout × (retries + 1) = 20秒
```

## ASCIIを書くときのルール

1. **幅を揃える**: 1行あたり60〜80文字以内（横スクロールを避ける）
2. **ラベルは短く**: `[コンポーネント名]` は15文字以内
3. **矢印のラベル**: 矢印の上か下に、プロトコル名・設定値を書く
4. **状態の区別**: 正常は `★` または `[稼働]`、障害は `×` または `[ダウン]`
5. **コンポーネントは5個以内**: 一枚絵は主要要素に絞る。詳細は解説セクションへ
6. **全角とボックス文字の混在に注意**: 幅が崩れる場合は半角スペースで調整

## Markdownでの表示

図解セクションでは、コードブロック内にASCIIを書く:

~~~markdown
## 3. 図解（ASCII）

```
  [あなたのアプリ]
        │
        │ リクエスト
        ▼
  [API] ──▶ [サーバー] ──▶ レスポンス
```
~~~

## よくある間違い

| 間違い | 正しい書き方 |
|--------|------------|
| 図解セクションが空 | 必ずコードブロックでASCIIを出力する |
| コンポーネントが多すぎる | 主要要素5個以内に絞る |
| 箇条書きだけで構造を説明 | ASCIIで視覚的に構造を示す |
| フローが複雑すぎる | 正常時→異常時→比較の3段階に分ける |
