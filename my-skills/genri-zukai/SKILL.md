# Genri Zukai

わからない技術を、一次情報で確かめ、「なぜそう動くのか」という原理まで掘り下げて、1 枚の HTML 図解にする。読み終えた人が、その技術のふるまいを自分で説明・予想できる状態をゴールにする。

製品の操作手順書や設定マニュアルは作らない。サイトへの投稿・デプロイ・共有はしない。写真や外部の画像は使わない。

## 基本ルール

- **返答・途中報告は日本語。**
- **確かめた事実だけを書く。** 一次情報（公式文書・仕様・提供元の解説・論文）で確かめ、出典に残す。確かめられないことは書かない
- **原理の 1 文が書けるまで、構成に進まない。** references/flow.md の「原理の掘り方」と「原理の 1 文」
- **見た目はテンプレートから作る。** `assets/template.html` を写して埋める。CSS を書き直さない。外部から何も読み込まない
- **質問は多くて 1 問、選択式で、推奨案を先頭に。** 依頼の文から決められることは聞かない。質問できない状況では推奨案で進め、報告で伝える

## 依存

このスキルのフォルダ（この SKILL.md があるフォルダ）を `<skill>` と書く。

| ファイル | 中身 | 読むとき |
|---|---|---|
| references/flow.md | 原理の掘り方・ページの骨組み・セクションの並べ方 | Step 2・3 |
| references/writing.md | 文体・見出し・用語・正確さのルール | Step 4 |
| references/design.md | 部品の使いどころ・外してはいけない約束 | Step 4 |
| references/figures.md | 図（SVG）の色・部品・型 | Step 4 |
| references/icons.md | 絵記号の一覧 | Step 4 |
| references/output-quality.md | 出す前の確認 | Step 5 |
| assets/template.html | 見た目の正本（CSS・表紙・全体像・セクション・まとめ・出典の形） | Step 4 |
| scripts/check.py | 機械の検査（外部読み込み・書き残し・図の字の大きさと色・番号） | Step 5 |
| scripts/shot.py | ヘッドレスの Chrome（Chromium）で、幅 800／390 × 明／暗を撮る | Step 5 |

## 動く場所と保存先

`/mnt/user-data/outputs/` があればチャット（claude.ai）、なければ Claude Code として扱う。

| 動く場所 | 保存先 | 作業用のフォルダ | 渡し方（Step 6） |
|---|---|---|---|
| Claude Code | `~/src/zukai/`（なければ作る） | スクラッチ領域、なければ一時フォルダ | `open "<ファイル>"` で既定のブラウザに開く |
| チャット | `/mnt/user-data/outputs/` | `/tmp/genri-zukai/` | 保存したファイルをユーザーに渡す（ダウンロードして開いてもらう） |

ファイル名：`<技術名>の仕組み.html`（例：`HTTPSの仕組み.html`）。

## 進め方

### Step 0: 依頼を受け取る

次の 3 つを依頼の文から読み取る。

- 技術名（何がわからないか）
- つまずいた場面（どこで出会い、何に困ったか）
- 知りたい深さ（言葉の意味か、動く仕組みか、なぜそうなっているかか）

つまずいた場面が読み取れないときだけ、1 問聞く。選択肢は依頼の技術に合わせて作り、推奨案（「動く仕組みを全体から」）を先頭に置く。

> 〇〇のどこが一番わからないですか？ 図解の入口（最初のセクション）をそこに合わせます。

ユーザーが「おまかせ」「そのまま作って」と言ったら、推奨案で進む。

### Step 1: 調べる

- 一次情報を探して読む。検索で見つけた解説記事は手がかりにとどめ、元の文書で確かめる
- 原理の中心になる事実（仕組みの手順・理由）は、2 つ以上の情報源で食い違いがないか確かめる
- 確かめた事実と出典（資料名・URL・確認日）を手元に並べる。料金・上限・版のように時期で変わる値は時点も控える

ネットにつながらず確かめられないときは、その旨をユーザーに伝え、続けるか聞く。続ける場合は出典欄に「一次情報で未確認」と書き、本文の言い切りを減らす。

### Step 2: 原理を掘る

references/flow.md を読む（省略しない）。「原理の掘り方」の ①〜⑤ に答え、「原理の 1 文」を書く。

**①〜⑤ に答えられ、原理の 1 文が書けるまで Step 3 に進まない。** 足りないところは Step 1 に戻って調べる。

### Step 3: 構成表を作る

references/flow.md の「ページの骨組み」「パートの決め方」「セクションの並べ方」に沿って、構成表（# ／パート／見出し／図の型／橋渡し）を作る。

構成表はユーザーに見せずに進める。ユーザーが「構成を先に見せて」と言ったときだけ、見せて確認してから書く。

### Step 4: 書く

references/writing.md・design.md・figures.md・icons.md を読む（省略しない）。

1. 保存先に同じ名前のファイルがあるか確かめる。あれば、上書きするか、名前の末尾に日付を付けて別に残すかを選択式で聞く（推奨は日付を付けて残す）。そのあと `<skill>/assets/template.html` を保存先へ写す
2. `{{ }}` の穴を埋め、構成表の順にパートとセクションを足す。テンプレートのコメントは消してよい
3. 図はセクションごとに、構成表で決めた型で描く。図の id には `f<番号>-` を付ける
4. 出典欄に Step 1 の資料を並べる

### Step 5: 確かめて直す（ゲート）

次の 3 つを、すべて通るまで繰り返す。**通るまで Step 6 に進まない。**

1. 機械の検査

   ```bash
   python3 <skill>/scripts/check.py "<保存したファイル>"
   ```

   誤り → 直してもう一度。注意 → 内容を見て、直すか、直さない理由を決める

2. 見た目の確認

   ```bash
   python3 <skill>/scripts/shot.py "<保存したファイル>" "<作業用のフォルダ>/shots"
   ```

   作業用のフォルダは「動く場所と保存先」の表のとおり（前回の画像は shot.py が消す）。撮った画像を読み、`pc-light` は全部、`sp-light` と `pc-dark` は図のある所を中心に見る。字のはみ出し、図の中の字の重なり、図の下の大きな空白、変な位置の改行、暗い画面で読めない字を探して直す。スマホ幅の図は、枠の中で横にスクロールする作りなので右側が切れて写るのが正しい

   Chrome も Chromium もない（チャットでよくある）→ 見た目の確認ができなかったことを報告に書き、3 に進む。このときは check.py の注意をいつもより丁寧に見る

3. references/output-quality.md を上から確かめる

### Step 6: 保存して報告する

- 「動く場所と保存先」の表の渡し方で、ユーザーに渡す
- 報告に書くこと：保存した場所（リンク）、原理の 1 文、セクション数と図の数、出典の数、確かめられなかったこと・単純化したこと・出典から推論して書いたこと

## やらないこと

- サイトへの投稿・デプロイ・共有（必要なら explain-page などを案内する）
- 製品の操作手順書・設定マニュアルを作る
- 写真・外部の画像・外部の CSS／JS／フォントを使う
- 確かめていない事実を、それらしく書く
- テンプレートの CSS を書き直す、色を足す
