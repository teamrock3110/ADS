# 提案文書の模範例

意思決定者の問いに、結論ファーストで答える提案文書の例。
すべての例は見出し記号 `■`、絵文字なし、markdown装飾なしで統一している。

文体はどの例もビジネスライティングのまま。変えるのは材料だけで、「■ 現状の課題」の最終行だけを場面（絵）で締める。
締めの場面が無い例（例1・例2・例3）は、材料が無いときに数字で終える形。無理に埋めない。

## 対話の流れ（例）

ユーザーが雑に投げ、AIが承認者を設計し、性質を判定してから材料を集める。

> ユーザー：Macアプリの申請フローを簡略化したい
> AI：承認者を設計しました。全社に影響が及ぶので室長ルートですが、室長はマネージャーの承認済みを重視するので、先にマネージャーへ出す2段構えにします。これでいいですか？
> ユーザー：OK
> AI：性質を判定しました。負担が申請者と一次承認者に移り、一度緩めると戻しにくい提案です。そのため「影響を受ける人と周知」「現行フローの経緯」「撤退条件」が必須材料になります。まず、今の一次承認が入っている経緯はご存じですか？
> ユーザー：2023年の導入時に未管理アプリが多くて、二重チェックにした
> AI：根拠になる数字はありますか？（なければ体験談でも可）
> ユーザー：申請は月42件、承認待ちが平均3.2日、差し戻しは6か月で0件
> AI：その場面も1つ聞かせてください。直近で承認待ちが起きたとき、何が起きていましたか。
> ユーザー：先週、新人が初日に使うアプリを申請して、承認が下りたのは3日後だった
> AI：確定情報を埋めます。開始日、試験期間、周知日を決めさせてください。

材料が揃ったら骨子で合意を取り、完成文を1回だけ出力する。

## 骨子の例（工程7）

完成文の前に1画面で出す。仮定を表に出して、本文に混ざる前に潰すのが目的。

```
■ 出す相手：マネージャー（1人目・承認）→ 通ったら室長（2人目・全社影響のため）
■ 結論1行：Macアプリ申請の一次承認を廃止し、事後監査に切り替えたいです
■ 使う数字：申請月42件、承認待ち平均3.2日、差し戻し6か月で0件
             （出どころ：申請フローの管理台帳）
■ 締めの場面：先週、新人が初日に使うアプリを申請し、承認が下りたのは3日後
             （ユーザーが対話で語ったもの）
■ 各セクションの主張
   現状の課題 ： 一次と二次の判断が同一で、待ち時間だけが増えている
   現行の経緯 ： 2023年の導入時は未管理アプリが多く、二重チェックが妥当だった
   提案内容　 ： 一次承認を廃止し、月次の事後監査で代替する
   代替案と却下： 自動承認のルール化 → 例外判定ができないため却下
   影響と周知 ： 申請者は待ち時間が短縮、一次承認者10名は作業が消滅。8/25に全社周知
   リスクと撤退： 未管理アプリ3件以上で一次承認を復活。11/30に報告
■ 仮定した点（違えば指摘してください）
   ・事後監査は私が担当する前提
   ・開始は9/1、試験期間は3か月
■ 体裁：Slack投稿 / profile の上限に従う / 絵文字なし / 装飾なし
```

## 例0：Before / After（上流を埋める効果）

同じ「定例会議を減らしたい」でも、上流（誰に・相手の問い・何を言い切るか）を埋めるかどうかで結果が変わる。

**Before（AIに丸投げ・上流が空っぽ）**

```
お疲れ様です。会議運営の効率化についてご提案がございます。
最近、会議時間の増加が生産性低下の要因として指摘されています。
つきましては、定例会議の頻度の見直しをご検討いただけますと幸いです。
```

丁寧だが、どの会議か・何がよくなるか・何をしてほしいかに答えていない。意思決定者は「それで？」となる。

**After（上流を埋めてから書く）**

```
【提案】報告だけの定例会議3本を隔週にして、浮いた月6時間を提案準備に充てます。ご承認をお願いします。

■ 現状の課題
定例会議は週7本・延べ12時間。うち報告だけの3本が週3時間を占める。
先週の30分の定例は、25分が資料の読み上げだった。7人中、口を開いたのは2人。

■ 提案する理由
報告だけの会議は資料の前日共有で代替できる。議論のある会議は残す。

■ リスクと対策
共有漏れを防ぐため、資料は前日17:00までに投稿するルールにする。
```

## メンツを守る言い換え（NG / OK）

同じ提案でも、過去を否定する書き方は通りにくい。状況の変化として語り、相手の功績を立てる。

**NG（過去を否定）**

```
今の定例会議は無駄が多く非効率です。やめるべきです。
```

**OK（状況変化＋功績を立てる）**

```
定例会議は立ち上げ期に足並みを揃えるのに役立ってきました。
人数も増えて自律的に動ける今、形を変えるタイミングだと思います。
まず1ヶ月、報告は資料共有に切り替えて試させてください。
```

## 説明 / 場面の言い換え（根拠の締め）

「非効率」「課題」などの抽象語は説明のサイン。その裏にある場面に戻して、根拠の最後の1文に置く。
**ここに書く場面は、ユーザーが対話で語ったものに限る。**材料が無ければ数字で終える。

| 説明（絵が浮かばない） | 場面（絵が浮かぶ） |
|---|---|
| 定例会議は非効率で時間が無駄になっている | 先週の定例30分のうち25分が資料の読み上げ。7人中、口を開いたのは2人だった |
| 申請フローの承認待ちが長く、業務に支障が出ている | 8/12に出した申請の承認が下りたのは8/15の夕方。その間、担当者は検証を止めて待っていた |
| 検知の確認作業が非効率になっている | 朝いちで同じアプリ名をJamf Protectで4回続けて開いた日があった |

書き方は3点。

- 数字を先に置き、**最後の1文だけ**を場面にする。文体は変えない
- 場面は1つだけ。「提案する理由」や「リスクと対策」には広げない
- 1行目は必ず結論。場面から書き出さない

## 例1：在宅勤務を週2日に増やす

```
【提案】在宅勤務を週2日に増やすことを承認してください。来月から3か月の試験運用にしたいです。

■ 現状の課題
通勤に往復2時間かかり、集中して作業する時間を確保しにくい。
資料作成は1人で進める作業が多く、出社の必要性が低い。

■ 提案する理由
移動時間を作業に充てられ、締め切り前の残業を減らせる。
週2日に絞れば、対面が必要な会議や相談は出社日にまとめられる。

■ リスクと対策
連携が滞らないよう、出社日を火・木に固定してチームで揃える。
3か月後に稼働と成果を振り返り、継続するか判断する。
```

## 例2：採用管理ツールの導入（金が動く）

金が動くので、費用対効果と比較した代替案が必須になる。

```
【提案】採用管理ツールをHRtable（月額3万円）で導入したいです。
Googleスプレッドシートで管理している採用フローを移行する承認をお願いします。

■ 現状の課題
選考状況の共有にメール往復が発生し、1件あたり平均30分かかっている。
スプレッドシートの更新漏れで、面接の重複が月2〜3件発生している。

■ 代替案と却下理由
・HRtable（月額3万円）— 採用サイトとAPI連携できる
・Recruit Board（月額2万円）— API連携できないため見送り
→推奨：HRtable（連携で更新漏れと面接重複を防げる）

■ コスト対効果
月額3万円に対し、現在の対応工数（月約20時間）を半減できる見込み。
```

## 例3：ノー残業デーの導入

```
【提案】毎週水曜日をノー残業デーにしたいです。
定時の18時退勤を原則とすることを承認していただきたいです。

■ 現状の課題
・定時以降は集中力が落ち、同じ作業でも時間がかかる
・平均残業時間は月40時間で、その時間帯の生産性は低い

■ 提案する理由
・終わり時間を逆算することで生産性が上がる
・残業の常態化を防ぐことで離職リスクを下げられる
・週1回から始めることでまず効果を検証できる

■ 補足
急ぎの仕事が入った場合は例外を認め、翌日に繰り越すルールとする。
```

## 例4：Slackのセキュリティ検知にAI自動返信を追加（負担が自分だけ）

負担が自分だけで完結し、金の動きも小さい。
そのため影響説明と代替案は置かず、費用の小ささとリスクの担保に重心を置く。
代替案を書くのは能力Bで「金が動く」がYesのとき。その見本は例2にある。

```
【提案】セキュリティ検知チャンネルにAI自動返信を試験導入したいです。
8/2から1か月、試験導入の承認をお願いします。

■ 現状の課題
検知チャンネルには毎日3〜5件の通知が届きます。
9割はMacへのAIエージェント系アプリ導入時の同種検知です。
毎回Jamf Protectを開き、アプリ名と安全性を確認しています。
この確認に月約6.7時間かかっています（5分 × 4件/日 × 20営業日）。
朝いちで同じアプリ名をJamf Protectで4回続けて開いた日もありました。

■ 提案内容
アラートからアプリ名を特定し、公式URLをスレッドに自動返信します。
担当者は確認の起点情報をすぐ得られます。試作は私が行います。

■ 費用対効果
・追加費用は Gemini API の利用料のみです（月100円未満の見込み）
・確認作業を月約6時間削減できる見込みです

■ リスクの担保
・Geminiに渡すのはアプリ名とイベント情報のみです
・最終判断は担当者が行います。自動クローズはしません
・9/2に精度を報告し、継続を判断します
```

## 例5：Macアプリ申請フローの一次承認を廃止（負担が第三者・戻しにくい）

負担が第三者に移り、一度緩めると戻しにくい。そのため「影響を受ける人と周知」「現行の経緯」「撤退条件」が必須材料に昇格する。

```
【提案】Macアプリの申請フローから一次承認を廃止し、事後監査に切り替えたいです。
9/1から3か月の試験運用として、承認をお願いします。

■ 現状の課題
申請は月42件で、承認待ちの平均が3.2日かかっています。
一次承認と二次承認の判断内容は同一で、差し戻しは直近6か月で0件でした。
先週は、新人が初日に使うアプリを申請し、承認が下りたのは3日後でした。

■ 現行フローの経緯
2023年の導入時は未管理アプリが多く、二重チェックが妥当な状態でした。
現在はJamf Proで配布可能なアプリが整理され、前提が変わっています。

■ 提案内容
一次承認を廃止し、申請から二次承認までの1段にします。
導入済みアプリは月次で私が一覧を突合し、想定外の導入を検出します。

■ 代替案と却下理由
・自動承認のルール化 — 例外の判定ができないため却下
→推奨：一次承認の廃止と事後監査（例外は人が見たまま、待ち時間だけ減らせる）

■ 影響を受ける人と周知
申請者（全社員）は待ち時間が3.2日から1.5日に短縮されます。
一次承認者（各部門の担当10名）は作業がなくなります。
8/25にSlackの全社チャンネルで周知し、8/29までの申請は現行フローで処理します。

■ リスクと撤退条件
未管理アプリの導入が試験期間中に3件以上発生した場合は、一次承認を復活させます。
11/30に申請件数と検出件数を報告し、継続を判断します。
```

## 例6：口頭で説明するときの手元メモ

提出チャネルが口頭のときは、貼り付け用の完成文ではなくこの形で出力する。
自分が見るためのメモなので、読み上げ用の整った文にしない。

```
■ 最初に言う1行
Macアプリ申請の一次承認を廃止して、事後監査に切り替えたいです。

■ 聞かれたら答える数字
申請は月42件、承認待ちは平均3.2日。差し戻しは直近6か月で0件。
一次承認者は各部門の担当10名。

■ 想定質問と回答
Q：未管理アプリが増えないか
A：月次でJamf Proの導入一覧を突合します。3件以上出たら一次承認を戻します。
Q：他部署から苦情は出ないか
A：申請者の待ち時間が1.5日に短縮されるので、苦情の方向は逆だと考えています。
Q：いつまでに決めればいいか
A：8/25に周知したいので、8/22までに判断をいただきたいです。

■ 合意を取りたいこと
9/1から3か月の試験運用として進めることの承認。
```
