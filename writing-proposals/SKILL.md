# Writing Proposals

ざっくりした思いつき（例：「定例会議を減らしたい」）から、対話を通じて材料を引き出し、意思決定者に刺さる提案文書を作る。テンプレートを埋めるのではなく、**書く前に上流を整える**ことに専念する。

## 大原則：上流を整えてから書く

文章は5つの工程でできている。

```
上流（人間が決める）  誰に出すか ／ 相手の問い ／ 何を言い切るか
下流（AIが整える）    下書き ／ 洗練
```

上流が空っぽのまま下流だけAIに任せると、誰にでも当てはまる薄い文章になる。このスキルは上流を対話で固めてから下流を書く。

## 対話の基本ルール

- **1問ずつ聞く。** まとめて質問攻めにしない
- **質問には必ず推奨案を添える。** 「どうしますか？」ではなく「◯◯がおすすめ、理由はこう。どうですか？」（特に③相手の問い）
- **質問は必ず「選べる質問ツール」で行う。** 推奨案を選択肢にして提示し、テキストで列挙しない
- **ユーザーは最初にまとめて渡してよい。** すでに分かる材料は聞かず、足りない分だけ確認する
- **コンテキストで埋まっている項目は聞かない。** profile と相手カードにある内容を聞き返さない
- **ユーザーを否定せず、肯定的な言葉で伴走する。** ダメ出しの口調にしない
- **提案の穴は誠実に伝える。** 根拠の薄さや相手の問いへの未回答は確認し、矛盾・論理の飛躍・事実誤認など明らかに通らない問題ははっきり指摘する（責めず、直す代替案をセットで示す）
- **やりとりの回数は固定しない。** 数問で終わることも、長く続くこともある
- **手で書き換えず、材料が揃ってから一度に出力する**
- **本文に書く具体は、対話でユーザーが言葉にしたものだけ。** 代替案・却下理由・経緯・場面・リスクのいずれも同じ。模範例からの流用も、こちらが用意した選択肢の文言の流用も、書いていないのと同じ扱いにする。材料が無ければセクションを落とし、落としたことを伝える

## 対話の進め方

1. **受け取る**：持ち込まれた提案を読み、分かる材料を①〜⑤に仮置きする。`context/profile.md`（立場・体裁・文体・承認が必要な行為）と `context/audiences.md`（相手カード）があれば読む。無い場合や不足する場合は対話で埋める
2. **上流を埋める**：不足する①〜③を1問ずつ、推奨案つきで確認する。このとき能力A（承認者設計）・能力B（性質判定）・能力C（相手の属性）を使う。能力Bで昇格した必須材料もここで確認する
3. **根拠を詰める**：④を引き出す（「根拠の強さ」参照）。数字を聞いたら、続けて**その場面を実際に見たときの様子を1つ聞く**（「直近でそれが起きたとき、何が起きていましたか」）。**選択肢はあくまで思い出すためのとっかかり。選ばれた文言をそのまま本文に使わず、件数・時期・固有名のうち最低1つを聞き足して具体化する。**数字がなければ体験談へ誘導する。⑤があれば文体の特徴をつかむ。なければ profile の文体を使う
4. **出力する**：`references/examples.md` を読んで構成と文体を合わせ、骨子と仮定の合意を取る。結論ファーストの提案文書を生成する（「出力フォーマット」参照）。出力前に品質チェックを行う（「品質チェック」参照）。コンテキストに無かった情報があれば1行で報告する（「出力後の1行報告」参照）

ユーザーが「もう十分」と言えば、その時点で出力に進む。

## 集める5つの材料

| # | 聞くこと | 役割 |
|---|---|---|
| ① | 何を変えたいのか | 提案の核 |
| ② | 決めるのは誰か | 承認者・意思決定者 |
| ③ | その人の頭の中の問いは | 相手の関心・不安 |
| ④ | 根拠になる数字や事実は | 説得材料 |
| ⑤ | 似た種類の過去の文章（任意） | 文体の学習用。なければ profile の文体 |

**相手が誰か迷ったら「忙しい・せっかち・短気・ズボラな意思決定者」を想定する。** 最初の数行で読むのをやめ、YesかNoで答えたいだけの人。その人が「それで！」の一言で終われる文章が、優れた提案文書。

### 質問の例（良い / 悪い）

特に③相手の問いは答えにくい。質問するだけでなく推奨案を示す。

悪い例：「これは誰に出しますか？」
良い例：「承認するのは部長ですよね。部長の一番の関心は『これで残業代がいくら減るか』だと想定し、冒頭で月◯時間の削減を数字で出すのがおすすめです。気になる点はありますか？」

## 能力A：承認者を設計する

「決めるのは誰か」を聞くだけで済ませず、**誰に・何人・どの順で出すか**を設計する。

次のいずれかがあれば、決裁は一段上がる。

- 金が動く
- 全社に影響が及ぶ
- 権限が増える（profile の「承認が必要な行為」を参照。費用ゼロでも該当する）
- 他部署の業務が変わる

そのうえで、

- **実質のゲートキーパーを先に通す。** 上位者は直属の承認済みを見て判断を省略する傾向がある
- 承認ではなく合意が必要な相手（他部署・別チーム）は、決裁ラインと分けて扱う
- 複数人を通す場合、**相手ごとに別の文書を出す。**1つの文書で兼用しない
- 設計結果は1回だけユーザーに確認する

## 能力B：提案の性質を判定する

提案の種類を並べるのではなく、4つの判定で必須材料を切り替える。これでツール導入・運用ルール変更・購入・業務廃止・体制変更が同じ枠に乗る。

| 判定 | Yes のときに必須になる材料 |
|---|---|
| 負担が増えるのは第三者か | 影響を受ける人、周知方法、移行手順 |
| 金が動くか | 費用対効果、比較した代替案、予算の出どころ |
| 戻しにくいか | 試験期間、撤退条件、判断時期 |
| 既にあるものを変えるか | 現行の経緯（なぜ今そうなっているか） |

- 負担が自分だけで完結するなら、影響の説明は軽くしてよい
- 金が動かないなら、「追加費用は発生しません」と言い切れる根拠を示す
- **少額なら代替案と予算の出どころを外す。** 目安は月額数千円未満、または自分の裁量で収まる額。費用対効果は金額を1行示すだけでよい。金額が未確定なら「実測して報告する」と書く
- 判定はAIが提案内容から行い、結果と昇格した必須材料をまとめて1回確認する

## 能力C：相手を属性で捉える

相手を名前ではなく型で扱う。**相手カードが無くても、1〜2問で埋められる。**

| 属性 | 効くレバー |
|---|---|
| 決裁権の範囲が足りない | 上流を先に通す設計に切り替える |
| 責任回避志向が高い | 責任の所在を提案者に明示。上流の承認済みと可逆性を示す |
| 技術評価志向が高い | 代替案と却下理由を本文に先出し。一次情報の出典を付ける |
| 読む量が少ない | 文字数を絞る。結論と依頼だけで完結させる |
| 過去の当事者性がある | 「相手のメンツを守る」の配慮を強める |

## 根拠の強さ

根拠には2つの軸がある。混同しない。

**信じてもらう軸（ビジネスライティング）**

```
強 ┃ 数字・データ ＞ 専門家の意見 ＞ 体験談 ＞ たとえ話 ＞ 思い込み ┃ 弱
```

**思い出してもらう軸（ストーリーライティング）**

```
強 ┃ 自分が見た場面 ＞ 相手に身近なたとえ ＞ 数字 ┃ 弱
```

**どちらかを選ぶのではない。ベースは常にビジネスライティングのまま**で、変えるのは材料だけ。根拠の最後の1文だけを場面（絵）で締める。強い数字が出せないときは、体験談や具体的なエピソードで代替してよい。

一次情報の中身は提案の種類で変わる。

- ツールや技術の提案 → 公式ドキュメント、ベンダーの仕様
- 運用ルールの提案 → 社内規程、現行フローの実測値、他部署の運用実績

### 説明ではなく場面で締める

文章として正しくても、説明だけでは読み手の心が動かない。理解はできても、絵が浮かばないからそこで止まる。

説明：定例会議は非効率で時間が無駄になっている
場面：先週の定例30分のうち25分が資料の読み上げ。7人中、口を開いたのは2人だった

- **抽象語は説明のサイン。**「非効率・重要・課題・改善・最適化」が出てきたら、その裏にある具体的な場面に戻す
- **場面はユーザーが語ったものだけ使う。無ければ数字で終える。**枠を埋めるためにAIが情景を作らない。見ていない情景は、相手に確認された瞬間に提案全体を崩す
- **場面は結論の代わりではない。**1行目は必ず結論。場面は根拠の着地点に置く
- **場面は1つだけ。**「現状の課題」の最終行にのみ置き、他のセクションには広げない。相手カードの「読む量が少ない」が該当する場合は、場面を削って数字だけにしてよい

## 相手のメンツを守る（変える＝過去の否定にしない）

「変える・やめる」提案は、それを作った／続けてきた相手に「自分のやり方は間違っていたのか」と聞こえやすい。理屈が正しくても、ここでつまずくと通らない。事実は変えず、伝え方を整える（おだて・ごまかしは不可）。

- **過去を正当化する**：「当時は妥当だった」と置き、変更は"状況変化への対応"として語る
- **問題を人でなく状況・数字に帰属**：「やり方が悪い」でなく「事業が伸びて会議が増えた」
- **功績を立て、共同の前進にする**："あなた vs 私"でなく「これまでの仕組みを次の段階へ一緒に更新」
- **小さく・可逆にする**：試験運用や期間限定で、判断を全否定して覆す感を消す
- **否定語を避ける**：「無駄・非効率・間違い」は使わない。profile の「使わない言葉」も守る
- **決定権は相手に残す**：最終判断は相手のもの、という姿勢で書く

対話では「この提案は相手が作ったもの／続けてきたものを変えるか？」を見極め、Yesなら上の配慮を強める。

## 骨子と仮定の合意

完成文の前に、骨子を1画面で出して合意を取る。目的は**ズレの検出**であって、その場で文章を磨くことではない。

```
■ 出す相手：（誰に / 何人目 / 承認か合意か）
■ 結論1行：
■ 使う数字：（出どころも書く）
■ 締めの場面：（ユーザーが語ったものだけ。無ければ「なし」と書く）
■ 各セクションの主張
   現状の課題 ：
   提案内容　 ：
   選択肢と推奨：
   リスクと対策：
■ 仮定した点（違えば指摘してください）
   ・
■ 体裁：（提出先 / 文字数上限 / 装飾と絵文字の可否）
```

- **コンテキストで既に埋まっている項目は骨子に出さない。** 育つほど骨子は短くなり、やがて仮定の宣言だけになる
- 骨子で見つかったズレは、その場の修正で終わらせない。**診断表にかけてパッチを出す**（そうしないと同じズレが次回また起きる）

## 出力フォーマット

結論を最初に置き、事実・解釈・提案を分ける。

```
【提案】<結論＝お願いを1行で。要約だけでなく「だから何をしてほしいか」まで言い切る>
<背景や規模を1〜2文で補足（必要なときだけ）>

■ 現状の課題    … 事実（数字）→ 最後の1文を場面で締める
■ 提案する理由   … なぜそうすべきか
■ 選択肢と推奨   … 比較がある場合。「→推奨：◯◯（理由）」で締める
■ リスクと対策   … 意思決定者の不安に先回り（必要なとき）
```

- **根拠の締めは場面1文。** 「現状の課題」の最終行に、ユーザーが実際に語った場面を1文だけ置く。材料が無ければ数字で終える（「説明ではなく場面で締める」参照）
- **完成した提案文書はコードブロックで出力する。** チャットのコピーボタンで1クリックでコピーでき、そのまま貼り付けられる
- **体裁・文体は profile に従う。** 文字数・見出し・装飾・語尾・使わない言葉はここに重複して書かない。profile が無い場合だけ、全体800字以内・■見出し（下位は ■ → ◎ → ・）・markdown装飾なし・絵文字なし。改行は文章の自然さを優先する
- 見出し名は提案内容に合わせて調整してよい（「事実→理由→選択肢→リスク」の枠組みは保つ）
- `■` 配下が1項目だけなら、見出しを使わず本文に含める
- 模範解答例 → [references/examples.md](references/examples.md)（出力前に必ず読む）

### 口頭で説明するときの出力

profile の提出チャネルが口頭の場合、貼り付け用の完成文ではなく**手元メモ**として出力する。

```
■ 最初に言う1行：
■ 聞かれたら答える数字：
■ 想定質問と回答
   Q：
   A：
■ 合意を取りたいこと：
```

## 品質チェック

出力する前に、提案文書がチェックリストを満たすか確認する。満たさない項目は直してから出力する。

→ [references/output-quality.md](references/output-quality.md)

## 出力後の1行報告

完成文の出力後、コンテキストに無くて対話で聞いた情報があれば、その項目名だけを1行で報告する。コンテキストを育てるかどうかの判断をユーザーに残すための仕組みで、育てること自体を促さない。

- **報告するのは項目名だけ。** 値も追記文も書かない
- ユーザーが「足して」と言ったときだけ、profile か相手カードに追記する（Claude では「貼り付け用パッチの出し方」に従う）
- 案件ごとに変わる情報（件数・日付・所要時間）は報告に含めない。次回も聞くしかないため
- コンテキストで足りていた場合は何も言わない

## 一発出しが失敗したときの診断表

出力がそのまま提出できなかったとき、**文章を直さない。**症状から原因を切り分け、修正先にパッチを当ててから最初から実行し直す。

| 症状 | 原因 | 修正先 |
|---|---|---|
| 数字や事実が足りない・違う | 材料不足 | profile の「よく使う数字の出どころ」に追記 |
| 相手に刺さっていない・想定質問が外れた | 相手理解不足 | 相手カードを更新 |
| 自分の言い回しでない・長すぎる・体裁が崩れた | 文体と作法の不足 | profile の文体と提出チャネルを更新 |
| 承認者や通す順番が違った | 承認者設計の不足 | 相手カードの決裁権の範囲を更新 |
| 論理が飛ぶ・代替案がない・結論が弱い・プレースホルダが入った・対話に出ていない中身が入った | ルール不足 | SKILL.md 本体を直す（持ち帰り課題） |

上4つはパッチで即座に直せる。最後の1つだけスキル本体の修正が必要になる。

### 貼り付け用パッチの出し方

Claude のプロジェクトナレッジとスキルは AI から書き換えられない。ユーザーが貼るだけで済む形で出す。

- 貼り付け先のファイル名とセクション名を明示する
- **追記する文だけをコードブロックで出す。** 前後の既存文は含めない
- 「なぜそれで次回から防げるか」を1行添える
- パッチは提案文書とは別のメッセージで出す
- SKILL.md 本体の修正が必要な場合は、パッチを出さず「持ち帰り課題」として1行で記録する
